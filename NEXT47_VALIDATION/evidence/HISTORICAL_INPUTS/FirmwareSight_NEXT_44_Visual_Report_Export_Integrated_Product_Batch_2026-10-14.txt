1. 本轮交付是“产品功能”，不是报表 CSS 修饰
====================================================================

必须交付五个用户可察觉结果：
(1) Analyze 一份单构建可视化概览：显示可信 Memory 指标、已知 Region、capability 和证据限制；允许导出一张清晰分享图与打印报告。
(2) Compare 一份双构建可视化概览：A/B/Delta、增长贡献者、同口径/不可比说明；导出图和可打印报告；保留原 JSON 与自包含 HTML。
(3) Release 一份审查友好概览：明确区分 Gate 判定、真实附件字节、Unknown、Release身份；不把 PASS 画成“可发布/安全认证”。保留现有完整 Bundle/Manifest/Verify 和原 release-report.html；在合法契约内提升打印可读性与图表。
(4) 可独立交付的 PNG 与 SVG 图像（真实可打开的文件，不是将 HTML 改名），在 PowerPoint、微信/钉钉、文档和邮件中可使用。PNG 的图像像素、尺寸和字体须经检查；SVG 自包含无外部资源。
(5) A4 Print-ready HTML（Summary + Detail）：可用本机浏览器“打印/保存为 PDF”；必须有针对纸张的分页与可读性设计。注意这与“软件原生直接生成 .pdf”不是一回事，不能误标功能名称。

P0 / MUST：PNG、SVG、独立 HTML + A4 print CSS、桌面可发现导出入口、验证与独立样张。
P1 / NICE-TO-HAVE：用户明确提及的原生 PDF 文件导出，只有已有安全无依赖路径能够可靠完成并有证据时才纳入。否则保持 PRINT_TO_PDF_VIA_BROWSER 而不是假装 NATIVE_PDF_EXPORT。不要为了“原生 PDF”引入 shell、Chromium 打包、打印机驱动依赖或网络服务。

产品定位：图表是可信表格和证据的“放大镜”，不是另一个数值真相源。工程完整详细报告和面向非技术读者的一页摘要并存；不因为做成领导版而隐去 Unknown、Review、来源限制或 Snapshot 与 Git 的身份区别。

3. A 单元：统一可信 Presentation Model（事实投影）
====================================================================

Implement a small, explicit, typed visual-report projection inside report/application layer, not Core truth logic.

Inputs may include existing AnalysisDocumentDto / analyzed snapshot projection, DiffResultDto, GateResultsDto, ReleaseBundleReport, or existing typed output. No reimplementing parser/diff/Graph/Gate/Release identity in TS/renderer. If existing DTO misses a fact, take it from the proper trusted domain boundary without altering public persistent schemas. Avoid creating a second giant persistent report format.

Semantic invariants:
1) byte counts always come from trusted Core state; KiB = bytes/1024 solely for display. Show actual bytes or accessible exact value. Do not round displayed 0.2 KiB into 0 when bytes are nonzero.
2) FLASH / Nonvolatile image footprint differs from RAM / Runtime RAM footprint; never combine them as a single used-memory figure, never claim region free space merely by subtracting summed sections from region end addresses.
3) capacity utilisation (%) is allowed ONLY when reliable matching region capacity exists, relevant footprint comparison is valid, capacity>0, and the current accounting model actually licenses it. Otherwise show `Capacity unknown`/`Usage not established` instead of a made-up progress bar. Must not treat sum(section sizes) as device flash capacity.
4) Build A / Build B/Delta must retain sign and comparability class. A missing side is absent, not 0. A newly added symbol isn't “grew from 0” without that definition in Core.
5) Growth contributors come from Core approved ranking and its source/basis; no renderer-side alternate sort that changes top-N meaning. If object/module attribution is not supported, don't invent named modules from symbol substrings.
6) Snapshot ID, firmware project release version, FirmwareSight app version, Git workspace HEAD, observed file hash and release ID are different identities and remain distinctly labelled; don't say Git commit built shipped bytes unless specific evidence proves it.
7) Gate states PASS/REVIEW/BLOCK/UNKNOWN/N/A have immutable meaning; visual status includes icon/word and supporting text, not colour alone; PASS is not ship authorisation or security certification.
8) Unknown/Declared/Observed/Derived classification survives projection. Missing MAP is a limitation, not a hidden success. No giant red “failure” graphic for unsupported inputs as if proven bad firmware.
9) Preserve original Rust config identity, file source and session state; no sanitized display value written back into DB/config.
10) All user-controlled names, symbols, paths, project strings, warnings, metadata and notes must pass an approved bounded safe-display projection BEFORE entering HTML/SVG/PNG or serialized DTO; escape correctly per context. Reject control chars, embedded host paths and markup tricks; preserve safe meaningful names when practical.

Deliver a compact internal chart-source model with documented invariants and tests that compare its numerical data 1:1 with existing DTO/CLI results across known/unknown/partial/mixed states. No opaque `serde_json::Value` soup for stable internal structure.

4. B 单元：图表设计与静态安全渲染
====================================================================

Design mandate: DESIGN.md “instrument-grade clarity”; frozen tokens are numerical truth source. Read them, don't mint colours/spacing. Chart priority table > ranked bars > compact stacked bar > treemap. No gradient, donut, 3D, neon, shadow, marketing hero, rainbow classification or colour-only status.

Required content and composition:
- One-page SHARE CARD suitable for 16:9 PPT / messaging: default image canvas 1600×900 px and SVG viewBox `0 0 1600 900` or an independently justified stable equivalent. This canvas is not the same artifact as A4 paper layout.
- Clear hierarchy: product / report type / case identity (sanitized), main FLASH and RAM facts, optional capacity when established, main Compare change (when comparable), up to five genuine growth contributors when established, evidence/provenance/capability qualification and a readable footer.
- Known/Unknown and N/A visual treatment must be unambiguous; every bar has numeric value, label, units, and valid measurement basis. No deceptive axis truncation or tiny-token placeholder graphs.
- For Compare, explicitly say A→B and use signed deltas. If rank limited, state Top N and include context for total changed counts.
- Release one-page card must give policy readiness without turning it into release approval. It may not imply authenticity from SHA-only integrity checks.
- Keep high contrast and CJK/ASCII readability where feasible with locally available system fonts; never download remote fonts. If binary SVG/PNG cannot faithfully render locale, explicitly restrict exported title language and document the limitation rather than outputting tofu without notice. Desktop bilingual controls still mandatory.

SVG:
- Real standalone well-formed SVG, with all styles and paths embedded, escaped XML, no <script>, foreignObject, remote href/url(), external images, embedded user input as CSS, event attributes, data exfiltration, external fonts, raw host paths or private project contents.
- Deterministic for identical fact input, locale, viewBox and renderer version (no wall-clock, random IDs, generated-at, temp filenames, absolute paths).
- Long symbol names and malicious labels clipped/ellipsized with accessible full numeric fact in a separate human-usable detail report; do not let overlap/hide disclaimers.

PNG:
- Actual standards-conformant PNG at documented px dimensions, not SVG renamed or screenshot stored in arbitrary content type. Prefer using same chart layout/scene graph as SVG to avoid divergent facts and designs.
- Evaluate existing crates and platform capabilities first. If a new small offline graphics/raster library is genuinely necessary, document precise why, feature surface, license, maintenance, dependency tree delta, size, trust boundary, why existing std/libs insufficient; run online cargo-deny four categories. NO uncontrolled shell/plugin/webview screenshot hack.
- Ensure geometry parity with SVG, legible text, safe handling of Unicode, long strings, unknown state. Decode exported PNG in an independent test to assert width/height/pixels and nonempty meaningful regions. Non-duplicated content semantics must be proven by a shared projection/scene model.
- If new dependency needs a frozen ADR/trust/security rule change, STOP that part for Owner decision; do not evade governance by pasting an unreviewed large PNG encoder.

Evidence:
- At least three representative synthetic variants with different states: single-build known, Compare mixed/unknown, Release with REVIEW/BLOCK distinctions; plus long/CJK/markup/Windows path canary. Test report fixture data only, never owner projects or confidential firmware.
- Use actual rendered visual previews/screenshots when environment supports a safe headless browser or SVG renderer. Test clipping, chart labels, whitespace, status icon clarity, print margins. If no viewer available, say VISUAL_NOT_VERIFIED and show programmatic proof separately; never fabricate screenshot evidence.
