继续往下挖之后，结论比上一轮更清晰了，而且已经开始从“框架 popularity”变成了“**成熟 Rust 产品实际上怎样组织工程**”。

截至 **2026 年 9 月 26 日**，我重新沿着你给出的 GitHub 条件检查了 `language:Rust stars:>10000`。当前查询池是 **253 个仓库**，分页结果正好是 `100 + 100 + 53`。在这个池子里，我目前已经进一步打开并核查了 **50+ 个代表性仓库**的 `Cargo.toml`、`package.json`、Tauri 配置等；下面的统计不是根据 README 猜技术栈，而是尽量从实际依赖文件里确认。

## 1. 先看这一轮最有价值的数据

我从这些项目里另外取了 **24 个实际产品仓库**，直接扫描顶层或主要 Rust crate 的依赖。

| 基础组件 | 24 个产品中出现 | 比例 | 我的判断 |
|---|---:|---:|---|
| **Serde** | 24/24 | **100%** | 几乎是 Rust 产品默认基础设施 |
| **Tokio** | 22/24 | **91.7%** | 异步产品事实标准 |
| **Reqwest** | 19/24 | **79.2%** | HTTP Client 基本形成共识 |
| **Clap** | 18/24 | **75.0%** | CLI/启动参数事实标准 |
| **Tracing** | 17/24 | **70.8%** | 生产级日志/Tracing 主流 |
| **Rustls** | 17/24 | **70.8%** | TLS 大量倾向 Rust-native |
| **SQLite** | 9/24 | **37.5%** | 本地产品非常重要 |
| **wgpu 直接依赖** | 3/24 | **12.5%** | 仅在真正需要 GPU 的产品里出现 |

这里有一个统计细节必须说明：`wgpu 12.5%` 是**直接依赖**，实际上会低估。例如 Sniffnet 使用 Iced，而 Iced 默认就可以经过 wgpu renderer；所以这张表不能解释成“只有 12.5% 用 GPU”。

反过来，**Serde 24/24、Tokio 22/24** 就非常有意义。

换句话说，如果今天要定义一个“现代 Rust 产品默认 Core Stack”，它已经相当接近：

```text
Rust Product Core

serde
  │
tokio
  │
  ├── reqwest
  │     └── rustls
  │
  ├── tracing
  │
  ├── storage
  │     └── SQLite / SQLx / rusqlite
  │
  └── interface
        ├── clap
        ├── Tauri
        ├── HTTP
        └── native GUI
```

这几个东西远比“Axum 还是 Actix”“egui 还是 iced”更接近真正的生态共识。

# 2. Serde 基本已经不是“选型”了

24/24。

包括：

Zed、RustDesk、Spacedrive、Cap、GitButler、Screenpipe、Rerun、Sniffnet、Neovide、Atuin、Anki、Qdrant、SurrealDB、Vaultwarden、Lemmy、Komodo、InfluxDB、Yazi、Zellij、Nushell、bat、Starship、DUFS、Clash Verge Rev。

全部都能在实际 Rust manifest 中找到 Serde。

这说明以后我们做 Rust 产品时，实际上没有必要再讨论：

> “JSON / config / IPC serialization 用什么？”

默认就应该首先考虑：

```rust
serde
serde_json
```

需要 TOML 再加：

```rust
toml
```

需要二进制协议，再根据场景加 MessagePack / CBOR / protobuf。

这和 Python 世界完全不一样：Rust 社区在 serialization 这一层已经高度收敛。

# 3. Tokio 也几乎已经成为产品默认 Runtime

24 个样本里 **22 个使用 Tokio**。

没有使用的两个：

- `bat`
- `Starship`

原因其实非常合理：它们主要是同步 CLI 工具，不需要大量网络、IPC、设备通信或异步任务。

不再是二选一：

```text

```

而是：

```text

+
Tauri App Shell
+
Native Rust Core

```

最典型就是 **Cap**。

它的 Cargo：

[Cap/Cargo.toml](https://github.com/CapSoftware/Cap/blob/main/Cargo.toml)

```text

```

```text

```

也就是说：

```text

    ↓
React

    ↓
Tauri

核心业务
    ↓
Rust

视频处理
    ↓
FFmpeg

    ↓

```

这其实是非常成熟的架构思想。

不是因为 GPU 很酷就：

> “全 App 用 wgpu。”

而是只有真正需要 GPU 的部分才用。

# 10. Native Rust GUI 其实已经分成了几个不同哲学

继续检查之后，这几个框架不能再简单放一张排行榜。

### egui

技术结构：

```text
egui
 ├── egui-winit
 ├── egui-wgpu
 └── egui-glow
```

官方 workspace 里现在同时支持：

`wgpu + winit + glow + wasm`

[egui/Cargo.toml](https://github.com/emilk/egui/blob/main/Cargo.toml)

它非常适合：

```text
Inspector
debugger
engineering tool
visualizer
internal tool
data UI
```

它的核心优势是：

> 开发速度。

---

### iced

Iced 当前默认 features 里面直接存在：

```text
wgpu
tiny-skia
```

而且其说明中明确：

```text
wgpu renderer:
Vulkan
Metal
DX12
OpenGL
WebGPU
```

[iced/Cargo.toml](https://github.com/iced-rs/iced/blob/master/Cargo.toml)

这意味着 iced 更接近：

> 正常 declarative application framework。

所以如果一定坚持：

**Pure Rust Desktop**

那么我现在会优先认真考察：

**Iced**

而不是 GPUI。

---

### GPUI

GPUI 最大优势还是：

Zed。

但问题也是：

Zed。

它的生态、组件、文档、使用场景仍然非常围绕 Zed 自身。

GPUI 更像：

```text
一个优秀产品孵化出来的框架
```

而不是目前已经像 React/Tauri 那样的：

```text
通用应用平台
```

所以我现在不会建议 MonoOLED 默认押 GPUI。

---

### Floem

Lapce 使用 Floem + wgpu。

它也证明：

> 纯 Rust 做复杂 IDE 完全可行。

但它目前面临和 GPUI 类似的问题：

生态规模。

如果产品本身不是 GUI framework research project，就需要谨慎。

**Tauri / Iced / Slint**

# 19. 对我们自己的 Rust 产品，我会把候选正式收敛成三个层级

结合我们现在正在做的 **MonoOLED-Studio V2**，以及这一轮实际高星项目数据，我已经不建议平行研究十几个 GUI 框架。

我认为只需要保留：

| 路线 | 定位 | 对 MonoOLED |
|---|---|---|
| **Tauri 2 + React + Rust** | 产品优先 | **主方案** |
| **Iced + Rust** | Pure Rust GUI | 备选验证 |
| **Slint + Rust** | 工业/嵌入式 GUI | 特殊备选 |
| egui | 工程工具 UI | 可参考，不作为主产品 UI |
| GPUI | 高性能 Native | 暂不押注 |
| Floem | Native Rust | 暂不押注 |
| GTK | Linux/传统 Native | 不适合作为跨平台主方案 |

这里不是给这些框架打“好坏分”，而是针对 **MonoOLED 的需求匹配关系**。

## 这一轮调研后的最大变化

上一轮我们主要得到：

> Tauri 是高星 Rust 桌面产品非常常见的方案。

这一轮进一步得到的是：

> **真正成熟的 Rust 产品并不追求“尽可能 Rust”，而是追求“Rust 放在最有价值的地方”。**

UI 有成熟 Web 技术，就用 Web。

业务核心需要可靠性，就 Rust。

设备通信需要 native，就 Rust。

需要 GPU，才 wgpu。

需要本地数据库，就 SQLite。

需要 async，就 Tokio。

需要网络，就 Reqwest + Rustls。

需要结构化日志，就 Tracing。

这已经是一套相当稳定的产品工程哲学。

下一阶段最值得继续往下做的，不是再随机翻仓库，而是把这 **253 个 `>10K Star` Rust 仓库正式做“分层分类”**：区分「最终用户产品 / 开发者工具 / Server / Database / Framework / Library / Language / 教程」，然后只针对真正的产品仓库统计 GUI、Tokio、存储、IPC、更新、安装包、测试、CI、商业模式。这样我们最终可以得到一份真正有统计意义的 **《2026 GitHub 10K+ Rust 产品技术栈普查》**，也能进一步回答“Rust 最适合拿来做什么产品，而不只是用什么框架”。
