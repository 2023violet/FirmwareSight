## 1. L26 problem statement, measured

`SHA256SUMS` at the repository root is the baseline manifest. It was generated by hashing **working-directory
bytes**, while the path set came from `git ls-files`, i.e. from the **index**. Those two halves disagree
whenever Git's checkout transforms a file's representation, and on this host it does: `core.autocrlf=true`
(system and global config both report it) plus `.gitattributes` `text eol=lf`.

Measured at the candidate tree, after this round's prompt, ADR and design record are all staged:

```text
tracked stage-0 entries   695   (692 before this round; +1 archived prompt, +1 ADR-0029, +1 this file)
unmerged entries            0
listed but absent on disk   0
worktree bytes != index blob bytes   13
root SHA256SUMS entries    693   (695 tracked - 2 paths whose basename is SHA256SUMS)
DIRECTORY_TREE.txt lines   813
```

The same manifest compared against **committed tree** blobs, head by head, shows the count is not a constant
of nature — it is whatever the writing host happened to have checked out at regeneration time:

| head | recorded digest != committed blob digest |
| --- | --- |
| `3400981` (Commit D) | 19 |
| `90aa69d` | 19 |
| `57a904e` | 14 |
| `bfbc1aa` | 14 |
| `859648e` (Commit E1) | **17** |
| `59d85c3` (Commit E2) | 13 |
| `80b47c4` (closure normalization) | 13 |

**That is the whole defect in one column: the number moved five times across seven heads without a single
intentional change of policy.** The "17" that every current document quotes (`INDEX.md:181`,
`.ai/CURRENT_STATE.md`, `.ai/HANDOFF.md`, `P5_PRODUCTIZATION_AUDIT.md:151`/`:687`,
`P5_COMMIT_E_DESIGN.md:336`, `P5_DIAGNOSTICS_RECOVERY_REPORT.md:268`, `P5_CI_AUTHORITY.md:65`) was true at
`859648e` and stopped being true afterwards. Commit F records the measured value instead of repeating it,
and dates the historical ones rather than rewriting them.

Two consequences the manifest could not express before this decision:

- The verifier that "checks" it re-reads the same working copy, so `RESULT PASS` on the writing host is
  agreement with itself, not reproducibility.
- No CI job or `check.py` step ran the verifier at all, so nothing outside this host ever disagreed with it —
  which is why a defect with a measured count of 13–19 files survived five stages.

## 2. The decision (ADR-0029), and why it is index rather than HEAD or worktree

**Root `SHA256SUMS` represents the SHA-256 of canonical Git stage-0 index blob bytes, not the raw bytes
currently present in the working directory.**

| candidate authority | can describe "what is about to be committed" | stable across `core.autocrlf` | stable across `git archive` | rejects a forgotten `git add` | verdict |
| --- | --- | --- | --- | --- | --- |
| working-directory bytes (today) | yes, accidentally | **no** | no | no | the defect |
| `HEAD` tree blobs | **no** — a staged new file has no HEAD entry | yes | yes | no | wrong: the manifest must be regenerable *before* the commit that changes it |
| stage-0 index blobs | yes — Git has already applied `.gitattributes`, clean filters and EOL canonicalization to staged content | yes | yes | **yes**, by construction: content that was never staged is not in the index | chosen |

At a clean committed checkout the index blob and the `HEAD` tree blob are the same object, so the rule is not
a third thing to keep in sync; it is the same bytes seen one step earlier.

`ADR-0028` (release identity is the exact bytes observed on disk) is **not amended, not superseded, and not
weakened** by this. The two rules live in different evidence domains, and the distinction is the point of
§6 of the prompt:

| domain | identity rule | why |
| --- | --- | --- |
| firmware artifact / MAP evidence / Release Notes / Release Bundle | ADR-0028: exact bytes on disk | those bytes are the product's evidence; normalizing them would change what a release claims |
| repository source baseline | ADR-0029: stage-0 index blob | the baseline is a claim about committed content, and must survive three OSes, two EOL policies, a clean worktree and `git archive` |
| distribution package `SHA256SUMS.txt` | raw artifact bytes | unchanged; a package checksum is a download check |

Three checksum domains, three generators, one sentence each in `P5_PACKAGING_REPORT.md:404-407`; Commit F
keeps them named so nobody reads one as another.

## 3. Generation workflow, and the guard that makes it self-enforcing

Closeout order (§8 of the prompt, adopted verbatim as the only supported sequence):

```text
1  edit intended source/docs
2  confirm no unrelated changes            git status --porcelain
3  stage all intended non-baseline changes git add <paths>
4  if the tracked path set changed:        generate_baseline_artifacts.py tree > DIRECTORY_TREE.txt
5  stage the tree                          git add DIRECTORY_TREE.txt
6  generate the manifest from index blobs  generate_baseline_artifacts.py sums > SHA256SUMS
7  stage the manifest                      git add SHA256SUMS
8  verify                                  verify_baseline_artifacts.py
9  run the full gate                       python scripts/check.py
10 inspect the staged diff                 git diff --cached
11 commit
```

Step 6 is enforced, not merely documented: `sums` mode **refuses to write** while Git reports a semantic
unstaged change to any tracked path, naming the paths. A line-ending-only worktree representation that Git's
clean filter maps back to the same blob is *not* such a change — the guard asks Git (`git diff`, not raw
bytes), which is precisely the discrimination §10 demands. The failure mode this closes is the exact one this
project has hit twice: edit a file, forget `git add`, regenerate a manifest over stale index content, and
believe the new work is covered.

`SHA256SUMS` and `DIRECTORY_TREE.txt` are excluded from that guard's own reasoning in the documented order:
the tree is staged at step 5 before the manifest is generated at step 6, and the manifest is self-excluded
from its own content by the basename rule it already uses. A new untracked file is not part of the baseline
until it is staged; after it is staged, it is. Both sentences belong in the generator's docstring, because
they are the two things a reader gets wrong.

## 4. Generator design

`scripts/generate_baseline_artifacts.py` keeps its CLI (`tree`, `sums`, stdout only, LF bytes via
`sys.stdout.buffer`) and its two artifact formats exactly as they are, so the change is confined to **where
the hashed bytes come from**:

- Path authority becomes the parsed output of `git ls-files -s -z` — mode, blob OID, stage and path, read as
  **bytes end to end**. That matters: two tracked paths carry non-ASCII names
  (`10_AUDIT/SOURCE_REVIEWS/…txt`, `10_AUDIT/SOURCE_REVIEWS_V05/…txt`), one of which also contains a space,
  and `core.quotepath` mangles them in any quoted form. `-z` output is raw.
- Any stage other than `0` (an unmerged entry) is a hard refusal, naming the paths. A manifest written over a
  conflicted index would certify neither side.
- Digests come from the canonical blob content of those OIDs, fetched through **one**
  `git cat-file --batch` process fed the OID list, not ~700 subprocesses. Measured on this host: one batch
  call returned all 693 objects with headers matching their OIDs and sizes.
- `tree` mode derives its path set from the same index parse, so both artifacts share one path authority.
- The basename exclusion (`SHA256SUMS`) stays as §9 requires. Its recorded consequence stays too:
  `golden/reports/p4-release/SHA256SUMS` is a *bundle* manifest in another domain and is therefore not an
  entry in the root manifest. That is documented in the audit, not papered over.
- Output format is untouched: `<64 lowercase hex><two spaces><path>`, sorted by path, LF, final newline, no
  host path, no self entry. Only 13 of the current 690 digests change value; 677 stay identical. That
  asymmetry is the evidence that this is a semantics fix, not a rewrite.

## 5. Verifier design

`scripts/verify_baseline_artifacts.py` remains **independent**: it imports nothing from the generator and
shares no hashing helper, so a bug in one cannot hide in the other. Independence is now structural, not
cosmetic — the verifier resolves content through a **different Git path**: it asks Git for `:<path>` (the
index's own view of the file) instead of a blob OID, so a mistake in OID plumbing, in the batch framing, or
in either parser shows up as a disagreement rather than as agreement.

Guarantees retained (all still reported, all still named the same where the meaning survives): malformed
entry, duplicate entry, listed-but-untracked (stale), tracked-but-unlisted, the manifest must not hash
itself, sorted-by-path, LF-only manifest and tree, no host path, and `DIRECTORY_TREE.txt` naming both
baseline files.

Guarantees **re-based** on the index, with the reason stated where they are printed:

- `hash mismatch` now means "the manifest digest does not equal the SHA-256 of the canonical index blob",
  and the diagnostic names the path and both digests' sources.
- `listed but absent` splits: absence **from the index** is a failure; absence **on this host's disk** is
  reported and is not a failure, because under ADR-0029 raw disk bytes are not the root-baseline authority.
  The line prints the reason so a reader who sees `1` does not read it as corruption.
- New: unmerged-index rejection, and a check that the worktree copies of `SHA256SUMS` and
  `DIRECTORY_TREE.txt` are byte-identical to their own index blobs — so the file you are reading is the
  artifact that will be committed, not an unsaved edit of it.
- New note printed with the result: raw working-directory bytes are not the root-baseline authority; the
  canonical external proof is `git archive <commit>` extracted outside the repository, then
  `sha256sum -c SHA256SUMS` over the extracted tree, which is expected to be all-OK because an archive
  carries canonical blob content unless an export transform exists. `.gitattributes` was read for such a
  rule and none applies to these paths; the archive proof in §7 measures it rather than assuming it.

Nothing in the verifier auto-fixes anything. It reports and exits non-zero.

## 6. CI integration

One new step in the `drift` group of `scripts/check.py`, running `verify_baseline_artifacts.py`. No new
workflow job; the authoritative job set stays **ten jobs**. `Generated output drift` gains a real step, which
is what makes L26 a closed limitation rather than a host-local one: from this head every push verifies the
manifest against the index on Windows, Ubuntu and macOS runners, three platforms whose checkouts previously
disagreed with the file silently.

Two implementation facts that make this step safe:

- It must never call `gate.skip()`: under `CI` a skip is a hard `return 1` (`check.py:453-456`), which is the
  rule this repository wrote after Run `37133706214` went green-ish on an unbuilt package.
- `actions/checkout@v4` leaves a real index, so stage-0 plumbing works in CI. That is checked in CI by this
  head's own run, which is external evidence and is therefore not asserted here — `P5_CI_AUTHORITY.md` and the
  run read are where it lands, and the failure mode if it is wrong is a red `Generated output drift`, not a
  silent pass.

Step counts are **reported as measured, never as expected**: the prompt's directions are drift 7 → 8 and full
gate 16 → 17, and a clean worktree's 18 (16 + the two cold-checkout asset steps) becomes 19. The number
actually printed after the change is the number that goes into every document, and ~40 prose claims across
`.ai/*`, `README.md`, `INDEX.md`, `BASELINE.yaml` and the P5 reports that quote the old counts are then
handled as a set: present-tense claims are corrected, historical measurements are dated, none is quietly
rewritten. `check.py`'s own comment that "this is the only step that looks at the index rather than the
working tree" becomes false with the new step and is corrected in the same edit.

"verifies only on the host that wrote it" expressed as an edit.

Every mutation is restored and the restore is verified by digest, and the round ends with a staged-diff that
names no product source beyond the L15 caption file. E, F and G are the three that could pass by accident;
each is run deliberately and its raw output kept.

## 8. L15 — closing only the display residue

The Architect's Option E stands unchanged: `SourceType::ElfProgramHeader` and the `analysis:1` token
`"elf.program-header"` stay, so no rename, no schema change, no migration 0006, no `analysis:2`, no rewritten
history. What Commit E recorded as a user-visible residue is closed here, presentation only.

The measured rendering chain, read at this head rather than cited from the closure report:
`crates/firmwaresight-storage/src/db.rs:507` stores `format!("{:?}", item.source_type)`,
`crates/firmwaresight-storage/src/query.rs:498-503` reads that column into `EvidenceRow.source_type` as a
`String`, `apps/desktop/src-tauri/src/details.rs:218-226` forwards it into `EvidenceRowDto`, and
`apps/desktop/ui/src/Details.tsx:667` renders `{row.sourceType}` under the `Source` label. So the string an
operator reads in the Evidence Inspector is the **Debug name** `ElfProgramHeader`; the kebab wire form is
produced only at `crates/firmwaresight-report/src/dto.rs:139` for exported JSON. That is the same
two-namespace fact L15 was written up around, and it decides the shape of the mapping.

Design:

- A closed, display-only caption table in `Details.tsx`, keyed on both namespaces — `ElfProgramHeader` (what
  storage produces) and `elf.program-header` (what any export-fed path could produce) — each mapping to
  **`ELF address + flags evidence`**. Same shape as `Compare.tsx:685-703`, which already keys `ElfAddressAndFlags`
  and `elf-address-and-flags` together; the repo has one precedent for this class and F1 reuses it instead of
  inventing a second.
- Caption text uses the prompt's wording (`address + flags`). `Compare.tsx:690` already prints
  `ELF address/flags evidence` for the same concept; both are accurate, the slash form is pinned by
  Commit E's L20 tests, and unifying two accurate captions would be a wording change wearing a fix's clothes.
  Recorded as wording drift worth one line in the final limitations document, not repaired here.
- Values outside the table keep rendering verbatim, exactly as they do today. Only the legacy identifier is a
  candidate for a caption: the other ten `SourceType` names in
  `crates/firmwaresight-core/src/domain/evidence.rs:40-53` are each a plain description of where the fact
  came from, and inventing ten captions nobody asked for would be a wording risk, not a fix.
- Styling follows `AGENTS.md` §11: a caption is a sentence, so it loses the `mono` class, while a verbatim
  identifier keeps it. `mono` in this design system is for numbers, hashes, versions, paths and tokens.
- Nothing stored, exported or persisted changes: the SQLite column, the DTO field, the portable schemas,
  the goldens and the Release Bundle all keep carrying the legacy identifier, which is what §20 requires and
  what the regression asserts.

Test: render a Details row whose stored `sourceType` is `ElfProgramHeader`, assert the user reads
`ELF address + flags evidence`, assert the raw token is **not** printed, and assert the same data still
carries the stored token (so the caption is proven to be display-only, not a rewrite). A second case proves a
non-legacy value still renders verbatim, so nobody can read the change as a general wording migration.

Final L15 status after that: **user-facing presentation residue = CLOSED; legacy wire compatibility debt =
CARRIED_FORWARD — LEGACY_WIRE_IDENTIFIER.** The limitation itself is not marked CLOSED, and a real rename
stays locked behind a future `analysis:2` under separate authority.
