## 2. Preference storage semantics, stated plainly

- **Where**: `app_config_dir()`, resolved in Rust and never supplied by the WebView. On the desktop that is
  `config_dir()/<identifier>` (`tauri-2.12.0/src/path/desktop.rs:239-245`). Measured on this Windows host, the folder
  the running application actually used is `%APPDATA%\com.firmwaresight.desktop` — and because Windows' config and
  data root are the same directory, **`settings.json` sits beside `firmwaresight-p0.sqlite` there**. That is not a
  second store and it does not disturb anything: `diagnostics.rs:287-308`'s `backup_names` lists only siblings
  starting `firmwaresight-p0.pre-migration-` and ending `.sqlite`, so an unexpected `settings.json` cannot enter the
  diagnostics payload. On Linux and macOS the two folders differ; that path is unmeasured here.
- **What**: one document, `{"schema_version":1,"size_unit":"bytes","startup_page":"analyze"}` — the bytes below are
  from the real file the real application wrote on this host, with no stray `.tmp-<pid>` left behind.
- **How it is written**: a sibling temporary file, then `std::fs::rename` over the target, then the result is read
  back through the same parser that will read it at the next start. A save that "succeeded" into bytes no load can
  read is not reported as a save.
- **Windows replace semantics, tested rather than assumed**: `saving_twice_replaces_the_document_and_leaves_no_temporary_behind`
  performs the second overwrite on this host, which is the case a UNIX-only mental model gets wrong — Rust's `rename`
  maps to `MoveFileExW` with replace-existing, and it fails while another program holds the file. A failure of the
  replace is `ERR-PREFS-8003`, the temporary is removed, and the old document is untouched.
- **Damage is never destroyed**: a load writes nothing, ever. Bytes that are not this build's document are copied to
  `settings.json.unreadable` by the *save that replaces them*, and if that copy fails the save refuses instead of
  discarding the person's last settings. `Recovery::Corrupted { preserved }` reports what is on hand, so the page can
  promise recovery as a fact rather than as a hope.
- **A newer version is not re-interpreted**: `schema_version` is probed loosely first (unknown keys in a newer
  document are not damage), and a save refuses with `ERR-PREFS-8004` rather than silently downgrading it. `reset()` is
  the one path allowed to replace it, because a person asked for that by name — and it still keeps the bytes.
- **Two saves in one window** take a mutex around the whole check-keep-write-replace-read sequence, so the last one
  to hold the lock is the last one on disk. Two saves from two *processes* are not serialised; see §6.
- **No folder at all** is not a startup failure: `Store::new(None)` answers with defaults, the page says
  `nowhereToStore`, and a save refuses with `ERR-PREFS-8001` instead of reporting a write that landed nowhere. The
  store's own failure path (`app_data_dir`) still aborts through `startup::StartupFailure` exactly as before — a
  missing database is a different fact from a missing preference file.

## 3. What is genuinely working, and what is not

Real today: `display.size_unit` (bytes/KiB, default bytes, bidirectionally synced with every page that shows a
switch, persisted across processes) and `startup_page` (Analyze / Bundle & History, applied once at boot, and only
when the reader has not already chosen a page). General states the storage fact and the local-first fact the
capability surface supports, and links to the existing Help/About/Diagnostics page rather than restating it.

Deliberately **not** done, and not faked with a disabled control: theme (System/Light/Dark) is B1-U2, language
(System/zh-CN/en) is B1-U3. No i18n or theme dependency was added, no unused preference fields were pre-declared,
and `settings.test.tsx` asserts those words do not appear on the page. Reset is implemented and asked in place.

Two v0.2 deviations, recorded rather than smoothed over:

1. v0.2 §3 names the second preference `startup_destination: analyze|last_page`. This round ships
   `startup_page: analyze|history` — a static choice, not a restored page. `NEXT-02` §3D allowed exactly this
   ("仅当可安全保留页面状态，且不复活旧 Gate 判定") and the Owner picked the selector. The reason for refusing
   `last_page` is a truthfulness reason: restoring the Release page would resurrect the *appearance* of a Gate run
   whose session state is gone, and `BASELINE.yaml`'s C1-U4 findings already record that the Gate page's verdict panel
   and its selectors can disagree. A static choice cannot do that.
2. v0.2 §3's A-group also lists `recent_history_*`, `language`, `density`, `font_scale`, `address_format`. None is
   implemented here, because none has a surface that would honour it today; `NEXT-02` forbids padding the page with
   placeholders.

## 6. findings reported, not fixed

- **A `settings.json` and the store share one folder on Windows.** Harmless today because `backup_names` filters by
  prefix, but it means "the application's own settings" and "the application's data" are physically adjacent, and any
  future folder-wide operation (export a support bundle, clear the folder) would reach both. A per-user decision to
  make before something ever walks that folder.
- **No cross-process write lock.** Two running windows can each write the document; the last one wins and the earlier
  one's own read-back is unaffected. The single-window case is what this unit promised.
- **`Session::preferences()` and `use_preferences()` are `pub`.** They are `pub` for the T03 test — `Session::open` is
  already `pub` for the same reason — and a WebView cannot reach them. A later round that dislikes the widened surface
  can move that test into `lib.rs`'s unit module instead.
- **The Start page choice is applied by a `useEffect` race guard, not by a resolution.** `readerChosePage` is a ref
  set by any navigation; if a reader navigates in the same tick the shell's read resolves, the read wins for the unit
  (correct) and loses for the page (intended). It is small, but it is timing logic, and timing logic deserves naming.
- **`ERR-PREFS-8005` (an off-set word from a caller) has no reachable producer through the UI today**, because the
  TypeScript union cannot express one. It is kept because the command takes `String` — matching `set_release_attachment_kind`'s
  edge, which is this crate's newest convention — so the refusal exists for a hand-built call rather than for a click.
- **The 1024×720 floor is not enforced by the window config** (min is 720×480), and no test measures layout at that
  size. v0.2 §9.3 asks for it; this round neither meets nor refuses it, it reports the gap.

## 9. next — B1-U2 and B1-U3, without starting either

- **B1-U2 (theme)** needs one thing from this round and nothing more: a single read/update path. A
  `appearance.theme` field belongs beside `size_unit` in `SettingsFile`, which means `SCHEMA_VERSION` and the
  `deny_unknown_fields` document change together — a versioned bump decision, not a field insertion, and the
  `unreadable`/`futureVersion` paths already handle an older build meeting a newer document. `AGENTS.md` 11 and ADR-0018
  currently forbid a Dark theme in the MVP, so **B1-U2 cannot begin without an ADR-level decision**; that is a human
  question this round does not pre-empt.
- **B1-U3 (i18n)** needs the *copy* to stop being inline. This round's page continues the house habit of sentences
  written into components, so its strings join the ones every other page already holds; a language switch should be
  specified as a translation layer over that whole set, not as a new island. The preference field itself is the same
  insertion shape as theme's.
- Both should reuse `Store`'s save/read-back and the four `ERR-PREFS` codes rather than inventing a second mechanism,
  and both inherit this round's rule: a control appears only when it does something.
