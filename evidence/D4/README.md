# D4 preparation: a same-origin ArmClang / armlink sample

Request: [06_DELIVERY/14](../../06_DELIVERY/14_D4_ARMCLANG_SAMPLE_REQUEST.md). Standing Owner rule 3 holds: **this is not a support claim.** FirmwareSight has no armlink MAP adapter, and armlink MAP files stay `NOT_SUPPORTED`.

## What exists now (Observed, 2026-10-17)

- **Toolchain:** the Owner's licensed Keil MDK Plus 5.43 on the development host, with Arm Compiler for Embedded 6.24 (`armclang` 5f371800, `armlink` 5f371500). Nothing was downloaded.
- **Sample:** `fixtures/elf/d4-armlink/{base,target}`, generated by `scripts/gen_d4_armlink_fixtures.py`. It is the M2 attribution project, built with armclang and armlink instead of GCC and GNU ld.
  - Each build has a same-origin set: `firmware.axf`, the armlink `--map --list` output with `--info=sizes,totals,unused` and `--symbols`, the scatter file `objects.sct`, the sources, and `fixture.toml` with the exact tool versions and every command line.
  - `target` grows the IMU table and links one more library member (`libdrv.lib(spi.o)`).
  - **Licensing:** the sources were written for this project, and `--no_scanlib` keeps the Arm C library out of the image, so the files can be committed. The image is a shaped sample for reading, not a program to flash.
  - **Paths:** all relative; the generator refuses an absolute path in the MAP.
- **Independent cross-check:** `scripts/crosscheck_d4_armlink.py` writes [CROSSCHECK.md](CROSSCHECK.md). armlink's own totals agree with GNU readelf (a reader from a different toolchain) on both builds.

  | Build | armlink RO / RW / ROM | readelf RO / (RW data + ZI) / ROM |
  |---|---|---|
  | base | 104 / 12 / 108 | 104 / 12 / 108 |
  | target | 188 / 44 / 192 | 188 / 44 / 192 |

## What FirmwareSight does with it today, per layer

| Layer | Result on this sample | Status |
|---|---|---|
| ELF read | Reads both AXF files. Sections are named after execution regions (`ER_IROM1`, `RW_IRAM1`). | Observed on one synthetic sample; **not a supported claim** |
| Memory accounting (ELF only) | Flash 108 / 192, RAM 12 / 44, `exact`, layout `none`, not admissible for a hard block. Equal to armlink's and readelf's totals. | Observed on one synthetic sample |
| armlink MAP | Refused with `ERR-MAP-3001` ("not from a supported linker"). This is correct: it is not misread as GNU ld. | `NOT_SUPPORTED` |
| Object and library attribution | Not available: it needs the MAP. The listing carries per-object and per-library-member rows (`libdrv.lib(spi.o)`), padding and a common symbol (`anon$$obj.o`), which is what an adapter would read. | `NOT_SUPPORTED` |
| Compare | The totals compare correctly (+84 Flash, +32 RAM). **Finding:** armlink names the RW-data and ZI output sections the same (`RW_IRAM1`). Name pairing leaves them unpaired, so they show as 2 added and 2 removed instead of 2 changed. | Defect to solve in the D4 adapter design |

## What the sample does not cover (why D4 still wants a real project)

- RW **compression**: armlink compresses RW initialization data by default when it pays off. With 4 bytes of RW data this sample never triggers it, and that is exactly the load/execution difference the D4 grammar has to handle (`04_TECH/39`).
- A **Keil IDE (µVision) build**: this sample used the command line only.
- Arm C library or microlib, an RTOS, a vendor startup file, CMSIS packs, overlays, multiple load regions, `__at` placement.
- A **real project's** size and shape. A synthetic sample can confirm grammar but not field use.
