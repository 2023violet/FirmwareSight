09_ADR/ADR-0029-repository-baseline-checksums-use-git-index-blobs.md

Status:

Accepted

Canonical decision:

THE ROOT REPOSITORY `SHA256SUMS`
REPRESENTS THE SHA-256 OF CANONICAL GIT STAGE-0 INDEX BLOB BYTES,
NOT THE RAW BYTES CURRENTLY PRESENT IN THE WORKING DIRECTORY.

At a clean committed checkout:

stage-0 index blob bytes
=
HEAD tree blob bytes

At pre-commit generation time:

stage-0 index blob bytes
=
the exact canonical bytes intended to be committed.

This is the repository source-baseline domain.

It is deliberately different from ADR-0028.

ADR-0028:

FirmwareSight firmware release identity.

Rule:

exact bytes observed on disk / shipped into the Release Bundle.

Why:

ADR-0029:

FirmwareSight repository baseline integrity.

Rule:

canonical Git stage-0 index blob bytes.

Why:

the repository baseline must be stable across:

- Windows / Linux / macOS
- `core.autocrlf`
- checkout line-ending transformations
- clean worktrees
- `git archive`

Do NOT use ADR-0029 to normalize:

firmware artifact bytes
MAP evidence bytes
Release Notes bytes
Release Bundle bytes

Do NOT weaken ADR-0028.

Different evidence domains have different identity rules.

7. WHY INDEX, NOT WORKING TREE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The current root baseline generator:

- gets path names from `git ls-files`
- hashes file bytes directly from the working directory

That mixes:

canonical Git identity

with:

host checkout/smudge bytes

and caused L26:

17 entries measured different from a clean checkout/archive.

The index is the correct pre-commit source authority because Git has already applied:

.gitattributes
clean filters
EOL canonicalization

to staged content.

This allows the generator to describe:

"what is going to be committed"

before the commit exists.

Do NOT define the root baseline as:

arbitrary working-directory bytes.

Do NOT define it only as:

HEAD blobs

because that cannot describe staged new/modified files before commit.
