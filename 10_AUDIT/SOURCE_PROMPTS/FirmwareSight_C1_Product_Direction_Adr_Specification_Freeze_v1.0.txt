0. 授权语义（必须先读）
========================
本提示词是为产品所有者准备的“下一轮执行授权文件”，不是架构师已经擅自批准 C 的证明。

【Owner 授权条件】只有产品所有者亲自将本文件交给 Coding Agent 并明确要求执行时，才构成以下两个决定：
  OWNER_PRODUCT_DIRECTION = OPTION_C1
  OWNER_AUTHORIZED_UNIT = C1_ADR_AND_DESIGN_FREEZE_DOCS_ONLY

该选择的含义：
  - Analyze 继续仅分析 ELF（GNU ld MAP 为可选辅助证据）。
  - .bin / Intel HEX 是 Release 侧附属“发布字节证据”，只做原始字节、大小、SHA-256 和有限的来源/声明状态记录。
  - C1 与 C3 的边界：选择 C1 —— 附属发布产物必须能进入 Gate 的 required-artifact 判定，并被 Gate 输入身份绑定，而不是仅打包、不参与 Gate。
  - 不声称 BIN/HEX 能被解析为 ELF 的 Section/Symbol/Memory/Entry Point，不声称 Intel HEX 地址跨度或记录校验和已核实。
  - 这是一项产品方向与文档设计的授权，不是实现授权，也不是批准升级或替换任何 V1 cohort 构建。

如本文件仅作为分析材料出现、并非 Owner 发出的明确执行指令，或 Owner 明确选择了 A / B / C3 / 暂缓，则 STOP，先请求确认；不得将“推荐 C1”擅自视为批准。

3. 必须正式裁决的六个技术问题
========================
D1｜分析输入 vs 发布附件的实体边界
- 一个分析对象依旧是必需的 ELF；可选 MAP；不得创造 BIN-only 的假 BuildSnapshot，不得把 BIN/HEX 作为 Section/Symbol 为空的伪构建加入 Compare。
- ReleaseAttachment 是附属于一次发布准备上下文的另一类实体。其权威持有者、何时选择、何时哈希、何时产生 GateContext、何时被 Bundle 收集，都必须在规格中指定唯一生产路径。
- 不得改变 SnapshotId::compose 的含义，不得暗中改变 analysis:1/diff:1 的已有事实。

D2｜附件身份、Gate 时序和抗 stale-PASS
- C1 的 required = ["bin", "hex"] 必须有真实、可验证的满足路径；“词法允许却永远 BLOCK”不能延续。
- Gate canonical input 必须绑定每个被评价附件的类型与实际字节 SHA-256；明确名称/路径是否也是身份的一部分，顺序、重名、多个同 kind 文件的规范化与稳定排序规则。
- 同一 ELF+MAP，仅更换 BIN 字节：旧 Gate 不得依然有效；重复相同输入：Gate 身份必须稳定。
- 附件被修改、替换、删除、增加、重命名后，何时重新计算、何时拒绝导出、何时需重新 Gate，写成确定的状态转移及错误路径。
- 必须区分“文件存在”“文件内容读取并校验”“是否真实来自此 ELF/Git 构建”。最后一项如果不可证明，就是 Unknown，不得提升为 Observed。

D3｜公开契约与版本策略（本轮最高风险关口）
- Gate run_id 当前由 firmwaresight-gate-input/1 的 canonical input 得到；Gate-results v1 包含 run_id + snapshot_id，但尚未表达 snapshot 之外附件的身份依据。
- 设计必须选定一个清晰且可复算的规范方案：例如经授权的可选 extensions 附件摘要说明，或 gate-input 版本升级与对应公共契约升级；两者不可含混，也不能用 extension 字段绕过“语义改变需 major”的 04_TECH/26 强规则。
- 给出旧 Gate Run/旧 Release Bundle 的读取语义；不能要求已保存证据被静默重写；不能让同一 schema major 被两种不可区分的语义解释。
- 对 analysis:1、diff:1、gate-results:1、accepted-reviews:1、release-manifest:1、project-config:1 逐项列出字段变化、语义变化、version/extension 选择与具体 contract tests。
- 若明确证明该方案必须进行未获 Owner 授权的 major 变更或既有证据身份重定义，STOP，提交兼容性影响与两种可选策略，等待新授权。绝不能自行推进 C3 或实施破坏性升级。

D4｜Bundle 与发布源一致性
- 扩展源码现有 verify_sources、InputChecks、PlanStale 的设计边界，让附件和快照行受到同等 digest/size/source membership 约束；Gate judged A、Bundle ships B 必须不可发生。
- 分清 bundle 内真实分析输入与被发布输出；Bundle 内只允许安全、规范的相对路径，禁止泄露绝对主机路径。
- 说明不同目录同名文件、Windows 大小写折叠、非法相对路径、符号链接、TOCTOU、目录外路径、空文件、超大文件的处理。不能在预览和导出采用不同规则。
- Release ID 和 manifest 现有 hash chain 不得失真；若附件使 bundle 字节变化，相关发布身份必须变化；既有校验器的兼容边界必须说明。

D5｜证据等级与 Intel HEX 限制
- 原始字节、长度、SHA-256：从实际读到的文件取得，Observed。
- 来自用户选择的 kind：Declared；来自后缀或文件头启发式：Derived，并说明依据与不确定性。不要把后缀当格式校验。
- Intel HEX 记录校验和、有效性、地址跨度、装载内容、Sections、Symbols、Memory、Entry Point、Object Attribution：本阶段一律 Unknown / Not verified，不能编造、不能当作 0。
- .hex 扩展名但内容异常时：可以在“未经格式验证的原始字节附件”策略内保留，但不得向 Gate/Bundle/接收方断言其有效 Intel HEX。若影响 required-kind 规则的语义，给出明确对策和负向测试。
- 不新增 HEX parser、不新增跨平台文件格式识别引擎。

D6｜UI / CLI / 工作流分层
- Analyze 文案 = 选择 ELF linker output 进行分析；MAP 可选。
- Release 文案 = 附加真实发布文件，包含 BIN / HEX；动词为 Attach / Ship 而非 Analyze。
- Gate 必须表达 required-kind 的可满足性、缺失、不可核验及具体拒绝依据；不因附件存在而推断它来自给定构建。
- Bundle 预览与导出显示文件名、byte size、完整 hash、证据等级和局限提示；内部实现是否显示 source path 必须遵守本地隐私边界。
- 不改变四动词导航，不引入设计新主题、不修改 tokens、不复制 mockup 中的虚构业务规则。
- UI/CLI 共用 Core/Application 真相，不让 React 重新计算哈希、diff 或 Gate。
