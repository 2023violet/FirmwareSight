【二、仅准许实现 C1-U1】
根据 04_TECH/28 §2、§3、§5、§7.7、§13 完成下列闭环，且每个节点只有一个权威事实来源。

U1-01｜领域与事实类型
- 在规定的 crate 边界加入 ReleaseAttachment 与 GateAttachmentFact，KindBasis 只允许 Declared 或 DerivedFromLeadingBytes（如确有依据），重用现有 ArtifactKind（Bin、IntelHex、Unknown）。
- 禁止将 Elf/Map 作为 ReleaseAttachment；必须返回可识别的拒绝结果，不能静默丢弃。
- attachment 的事实仅为原始文件存在性、byte_size、sha256 与 kind_basis；分析结构、原生 Intel HEX 记录有效性、地址跨度、内存、entry point、symbol、object、构建 commit 归属均不得被伪造。
- 区分文件名/宿主路径与证据事实；宿主绝对路径不得进入 Gate canonical text、快照身份或可移交公共证据。不得新增网络、Tauri 权限、依赖或将本机地址暴露给前端。

U1-02｜唯一的 observe_attachment
- 由 firmwaresight-project 提供唯一观测入口（适配已有函数命名和签名）。仅按用户显式选择的单个文件做 stat → 普通文件校验 → 拒绝零字节 → 流式 SHA-256 → 记录长度；不得使用为 ELF Parser 准备的整文件 GuardedInput::load，不得一次性把整个 BIN/HEX 读入内存。
- 复用已有 fingerprint::file_sha256 等安全机制。对不可读、非普通文件、空文件、禁止 kind，返回明确的类型化错误与不泄漏宿主路径的可用信息；不自行扩展目录扫描、glob 或递归导入。
- 观测与声明须分离；不允许仅凭扩展名把 Declared 升格为 Observed，不允许使用启发式格式判断推导出 HEX 有效或任何结构字段。
- 本轮通过 Core / Project 层单元与集成测试调用该入口；不新增 UI 按钮、CLI --attach 或用户可用的完整 Release 附件流程。

U1-03｜GateContext 与确定性身份
- 新增 GateContext.attachments 独立集合，不合并到原 GateContext.artifacts；现有 ELF/MAP 快照行语义原封不动。
- canonical input：附件集合为空时，firmwaresight-gate-input/1 的文本必须与交接 HEAD 逐字节一致，包含换行、排序、空值处理，所得旧 run_id 必须完全相同；不得为 /1 新增空 attachments 块或空字段。
- 附件非空时才使用 firmwaresight-gate-input/2；独立 attachments[... ] 块，行格式按 04_TECH/28 §5 与 ADR-0030 D-4/D-5；按 (kind word, lowercase sha256) 排序，完全相同的 (kind,sha) 只绑定一次，多件不同字节的同 kind 均绑定。
- Gate identity 不包含文件名、绝对路径、mtime、inode 或 size；size 作为独立事实保存并校验，摘要作为 Gate 身份基底；重命名同字节文件不改变 Gate run_id，变更 kind 或 bytes 必须改变 run_id。
- 遵守 SnapshotId::compose 完全不变；不改 release id grammar；不改变五态规则判断、effective severity、证据 Unknown 聚合或 Policy SHA-256 语义。
- 对现有全部 GateContext 构造路径使用显式 empty attachments 的兼容初始化。零附件行为不得有可观察回归。

U1-04｜Additive Storage Migration 与 re-read
- 新增单条 additive migration，优先按批准规格命名 0006_release_attachments.sql；先核查编号未被占用。
- 表应独立于现有 artifacts，名 gate_run_attachments，引用 gate_runs(id)，保存 ordinal、kind、sha256、byte_size、kind_basis；对合法 kind、64 位 lowercase hex 摘要、非零大小、主键及外键施加明确约束。参照 04_TECH/28 §7.7，不要将其当作可直接复制而不审核的 SQL。
- 原有 artifacts 表的 parser_id、architecture、bitness、endianness 非空约束不得放宽或用假数据填充；原有 migration 不得重写；不添加破坏性操作。
- 新 Gate run 的附件事实应与 Gate run 原子写入（事务）；重复 run_id + 不同附件事实必须拒绝，不得覆盖旧 Run。重读时按 canonical ordinal 恢复相同 Gate 上下文与 run_id。
- 现有旧数据库无需迁移手工处理即可升级，新列/新表不导致已有 run_id 改变；读取旧 run 必须自然得到空附件集。
- 仔细核查规格草案表中没有保存 source path，如何在“不存储原始附件字节”和“不把宿主绝对路径写入可移交证据”的约束下，可靠实现 persisted fact re-read。C1-U1 只需可靠还原被判断的事实；未来再观测与真正装包属于 C1-U2。若现有运行接口隐含“仅凭已保存事实就能重找原始文件”，不要编造这个保证，应如实区分；如必须违反 ADR-0030 才能实现，STOP 并提出明确设计冲突。
