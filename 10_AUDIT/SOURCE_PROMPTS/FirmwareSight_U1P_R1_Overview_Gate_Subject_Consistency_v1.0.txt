A. SAME CURRENT SUBJECT

When an actual currently analyzed selection is present AND
selection.selectionId === analyzedSelectionId AND
lastGood.identity.snapshotId === gateRun.snapshotId AND
there is no known current-policy provenance mismatch:

- Readiness may display Gate PASS/REVIEW/BLOCK/UNKNOWN in its normal prominent verdict strip.
- It MUST identify the actual Gate judged snapshot inside the verdict region using the full identity
  in accessible text (visual middle truncation permitted only when full value remains retrievable).
- Keep the run ID and run timestamp.
- Keep the existing finding counts, accepted-review semantics, and policy-readiness disclaimer.
- No recomputation of the verdict: take the Gate's own disposition and counts.

B. DIFFERENT SNAPSHOT

When gateRun.snapshotId !== lastGood.identity.snapshotId:

- The prominent readiness answer for the CURRENT displayed build MUST be NEUTRAL / NOT ASSESSED.
- It must clearly say the last Gate run evaluated A DIFFERENT BUILD.
- Show the judged Gate target snapshot ID (full accessible value) and the displayed current snapshot ID.
- Do NOT place an unqualified green PASS next to a different build's numbers.
- The old Gate run remains preserved, not deleted or falsified.
- If historical verdict details are shown, they MUST be explicitly labeled as historical/for the other build,
  visually subordinate to a neutral current-build state.
- CTA leads to Release Gate to choose/run the Gate on the intended build; navigation is not an implicit rerun.
- Keep policy/compliance disclaimer intact.

C. SELECTION CHANGED WITHOUT SUCCESSFUL ANALYZE

If selection exists but its selectionId !== analyzedSelectionId, even if
lastGood.identity.snapshotId === gateRun.snapshotId:

- Explain the CURRENT SELECTION has not been analyzed.
- Do NOT imply the old Gate verdict covers that new selection.
- The last-good analysis and old Gate may remain available if unmistakably scoped to the previous build.
- Do not clear last-good by default: U1R's valid retention contract stands.

D. NO ANALYSIS IN SESSION BUT GATE RUN EXISTS

- Do not call a historical Gate verdict a current-build ship decision.
- State there is a run for a named judged snapshot, but no currently analyzed selection to pair it to.
- Preserve ability to open Release Gate.

E. NO GATE RUN

- Keep the honest no-run empty state and navigation.
- Never synthesize a PASS or a zero finding count as evidence of a run.

F. POLICY CHANGED AFTER RUN

If loaded project.policySha256 and gateRun.policySha256 are both present and different:
- Do not represent the old Gate as judging the current policy.
- Explain the Gate run used a different policy fingerprint and the old result is retained.
- Do not invent a replacement policy or query new storage.
- Distinguish default-policy run semantics from explicit loaded-project policy semantics; do not
  treat null project or a default run as a fabricated fingerprint mismatch.

G. CONSISTENCY ACROSS PAGES

- Release Gate continues to display the Gate run's own original verdict and findings.
- History continues to preserve original run and subject identities.
- Overview is the place that must stop misattributing the run to a different currently shown build.
- A changed selection, newly successful Analyze or newly run Gate must update Overview correctly.

H. NO-GREEN-CURRENT-PASS IN MISMATCH

This is a strict acceptance invariant. Do not place any unqualified PASS/readiness sentence
for the CURRENT analysis in the mismatch or pending-selection state.

Acceptable implementation may pass analyzedSelectionId into Overview and derive one small
read-only presentation state. Keep presentation facts separate from domain truths.
