二、目标与范围
提升固件工程师实际使用 Release 附件和便携包时的可理解性与工具可靠性。不是扩充 BIN/HEX 解析，也不是重新设计 Settings/UI，更不引入新的分析/发布契约。只处理有可复现证据的四项缺口：

N01-F01 — `fwsight gate --attach` 的相对路径按 CWD，而 `fwsight release prepare --attach` 的相对路径按 `--project` 根解析；失败时 E-1 错误文案把“按另一个相对基准查找”误写成“文件消失”。
N01-F02 — 中文文件名如 `固件镜像.bin` 通过安全清洗后可能以 `bin` 出现在 UI；两个中文来源名称可能 UI 同名，而 bundle 归档名被消歧。需要区分“本机选中的显示名”和“便携包内的安全路径”。
N01-F03 — `scripts/verify_bundle_portability.py` 默认要求 `diff.json`，遇到**合法无 baseline** 的单构建 Bundle 直接 `FileNotFoundError`，而 bundle 自身 SHA256SUMS 与 manifest 可能全合法。
N01-F04 — 同一附件字节变化在 CLI 的 selected_run_id=None 路径可报告 6103/6118，在 Desktop 的 selected_run_id=Some 路径先报告 6102；两个代码不能被错误宣称完全一致。改善诊断解释，不改变身份、安全拒绝次序及错误码。

三、实施前的最小技术决策（写在单元报告，不要额外开长规划包）
A. F01 先把 `gate`、`release prepare`、`--project`、`--artifact`、`--attach` 的现有路径解析规则表格化并写出绝对路径与两种相对调用的直接实测。如果统一路径基准会改变既有 CLI 参数行为，**不要自行作破坏兼容的选择**。优先以明确、准确、可操作的 CLI Help/文档与拒绝文本解决本轮诊断问题；如果能证明一种一致规则符合既有 CLI 合同且没有可观察兼容破坏，才可在此单元统一并添加回归测试。若需要 CLI breaking semantics 或新版参数，STOP 那一分项并交 Owner 最小决策；其余独立任务继续。
B. F02 本机 UI 使用尽可能忠于用户所选文件的叶名（含 Unicode），绝对宿主路径不得进入 portable 文件、错误及诊断。bundle 内安全 `artifacts/` leaf、collision、SHA256SUMS、manifest、Release ID、runId 的字节合同保持完全不变。展示名与最终包内相对路径是不同字段/角色，不能用“重命名 bundle 内文件”掩盖 UI 问题。若缺少合法安全的显示名 Carrier，给出最窄 DTO 改动及兼容证据。至少 `固件镜像.bin`、`固件.bin`/`镜像.bin` 同时存在、`my image.bin` 三组测试，比较本机显示与归档名。
C. F03 无 baseline 是合法情形，先确定到底哪些文件对这种发行是必需的；只有 `diff.json` 缺席属于合法才跳过相应对比检查，**不得允许有 baseline 但损坏或丢失 diff.json 的 Bundle 误过**。其余 SHA256SUMS、Manifest、schema 及原有安全检查必须如常失败或通过。使用真实由 CLI 生成的有/无 baseline bundles 做正负测试；脚本退出码、PASS/SKIP/FAIL 需如实反映，而不是 traceback。
D. F04 公开说明目前 Gate 重新判断早于 Bundle staleness/refusal 的分支次序；至少各有一个直接测试覆盖 CLI 6103 与 Desktop 6102，明确两端不同但均 fail-closed、无意外落盘。不要改 Core、稳定 error code、有效性顺序或身份以求表面统一。
