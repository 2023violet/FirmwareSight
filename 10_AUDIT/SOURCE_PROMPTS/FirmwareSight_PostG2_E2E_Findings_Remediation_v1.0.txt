━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Architect accepted classification:

E2E-F001 = E2E-S3 / MINOR

Observed behavior:

After a successful Analyze result is visible,
the user selects a different artifact but has NOT pressed Analyze yet.

The page continues displaying the previous build's analysis.

The previous report is not clearly labelled as previous/pending merely because the selection changed.

This is especially misleading when both files have the same leaf name such as:

firmware.elf

Existing current implementation fact at HEAD:

`apps/desktop/ui/src/Analyze.tsx`

currently marks the summary stale when:

`error !== null`

and its existing stale note is designed primarily for a FAILED later analysis.

A new selection by itself does not make `stale=true`.

Required UX contract after fix:

When:

- lastGood exists;
- the user changes the current artifact selection;
- that newly selected artifact has not yet produced the displayed lastGood result;

the UI must clearly communicate:

the report below is the previous analysis
and the newly selected artifact is pending Analyze.

The old report MAY remain visible.

Do NOT blank useful last-good data just to fix attribution unless evidence proves that is the smallest/clearest solution.

Required properties:

- selecting a new artifact does not mutate lastGood;
- lastGood numbers remain truthful;
- no new snapshot is created before Analyze;
- Compare/Release still prefer the last actually analyzed snapshot, not merely selected candidate;
- failed Analyze continues to use truthful previous-analysis attribution;
- after successful Analyze of candidate, previous/pending label disappears;
- same leaf filename must not make the state ambiguous;
- MAP attach/remove on the pending candidate must not falsely imply lastGood changed.

Preferred implementation direction:

Track enough session-level identity to distinguish:

current selection

from:

selection that produced lastGood.

Do not use filename equality as identity.

A selection id / explicit analyzed-selection identity is preferable to leaf-name comparison.

However:

choose the smallest design consistent with current App/Analyze ownership.

Do not add this identity to portable schema or SQLite.

This is UI/session state only.
