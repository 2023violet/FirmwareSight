# 《可视化与文档导出 · 技术可行性简报》

> 议题：① 分析结果应用内可视化；② 文档导出（md/docx/xlsx/html 等）。
> 评估基座 = 冻结技术栈：Rust Core + Tauri 2 + React、本地优先、确定性输出、report crate。
> 阶段口径 = 产品路线（P0 MVP / P1 / P2 / Post-GA）。注意与工程交付阶段的对应：产品 P0 的 Release Bundle = 工程 P4（`firmwaresight-report` 的实现点），本文括号内注记工程阶段。
> 工作量口径：S ≤ 2 人日、M ≤ 5 人日、L > 5 人日（含测试与 golden 样张，不含 ADR 评审）。

---

## 0. 结论速览（TL;DR）

1. **可视化：不引图表库，走「自绘 SVG/CSS + 单点微依赖」路线。** 这不是我们的偏好，而是基线的明文裁决：FS-TECH-014 §Charts 规定 MVP「no chart library」、FS-TECH-012 将「large chart library」列为 Frontend No baseline。好在需求的四个形态（table / ranked bars / compact stacked bar / treemap）恰好都能低成本自绘，自绘反而是与无渐变/无阴影红线兼容度最高的方案。
2. **大数据量 symbols：性能问题主要不在前端渲染，而在数据过通道的方式。** IPC 红线（FS-TECH-015 §3「Never send the entire symbol table」）已经把正确答案写死了：Core 侧聚合 + 分页，前端虚拟化兜底（FS-TECH-014 已预留 "add row virtualization"）。
3. **导出：一个报告 IR + 多 renderer，全部挂在 report crate 的 ReportRenderer 端口下，不新增 crate。** HTML/JSON 是基线承诺（Bundle 成员），md/csv/xlsx 是低风险扩展，docx 是中等成本可选，**PDF 原生排版不值得做**（用 HTML 打印视图承接）。
4. **建议节奏：** P1 落 HTML（增强版）/CSV/MD/XLSX + ranked bars/stacked bar + treemap 首版；P2 落 DOCX + 跨 build 趋势；Post-GA 再议 PDF 打印视图与 ECharts 级重交互图表。
5. **不值得做清单（§5）：** 原生排版 PDF、PPTX、RTF/ODF、带公式的"活" XLSX、图表 PNG 光栅化导出、自研二进制格式。

## 2. 议题① 应用内可视化

### 2.1 React 图表库候选对比（兼容性 = 无渐变/无阴影/克制红线）

| 候选 | 渲染 | Treemap | Stacked bar | 大数据能力 | 体积(gz 量级) | 与 UI 红线兼容性 | 结论 |
|---|---|---|---|---|---|---|---|
| **自绘 SVG + CSS**（推荐） | DOM/SVG | d3-hierarchy 算法 | 原生支持 | 取决于我们（配合 §2.2 策略，无压力） | d3-hierarchy ≈10KB + react-virtual ≈4KB | ★★★★★ 颜色/边框直读 tokens CSS 变量，天然无渐变无阴影 | **主路线** |
| ECharts（按需打包） | Canvas/SVG | 内置强 | 内置强 | progressive/large 模式强 | 按需 ≈300–400KB，全量 ≈1MB | ★★ 默认样式是渐变+阴影重灾区，需全量覆写并 CI 治理风格漂移 | 仅 Post-GA 出现重交互需求时经 ADR 引入 |
| Recharts | SVG | **无内置**（硬伤） | 有 | 弱（10 万点级卡顿） | ≈100KB | ★★★ 组件化易约束 | 排除：treemap 缺失使我们仍要自绘，不如全自绘 |
| Chart.js | Canvas | 需第三方插件（维护一般） | 有 | 中（decimation 仅折线） | ≈70KB+插件 | ★★★ | 排除：插件质量与治理成本 |
| Nivo | SVG/Canvas | 有 | 有 | 中 | 按需 ≈100KB+ | ★★★ 主题化强但拖 d3 全家桶 | 排除：收益被自绘覆盖 |
| Visx（Airbnb） | SVG/Canvas | d3-hierarchy 拼 | 自拼 | 中 | 按需 10–40KB | ★★★★ 本质是"官方封装的自绘原语" | 备选：若嫌裸 d3 繁琐可在 spike 时二选一，不改变架构结论 |
| AG Charts | Canvas | **Enterprise 付费功能** | 有 | 强 | ≈300KB | ★★★ | 排除：许可与商业模型冲突 |
| Plotly / Victory / uPlot | — | — | — | — | — | — | 排除：Plotly 体积 ≈3MB；Victory 维护放缓；uPlot 仅时序，不做 treemap/bar |

**裁决与理由：**
- 当前可视化需求清单（表格、表格内嵌 ranked bars、单行 compact stacked bar、静态 treemap + 下钻）全部是**低交互、强排版约束**的形态——这正是自绘的最佳射程，也是设计哲学"Instrument-grade clarity"的直接推论：图表即表格的延伸，而非独立的图形世界。
- 引入任何"全家桶"库都会带来三重成本：① 体积与供应链（准入清单逐项过）；② **风格漂移源**——库的默认样式（渐变、阴影、动效）与红线持续对抗，等于把 FS-TPL-005 checklist 的一半条目变成"每次升级都要重新核对"；③ 确定性风险（Canvas 位图参与导出时不可逐字节复现，SVG 才可）。
- **未来引入图表库的触发条件（写进未来 ADR）：** 出现跨 build 趋势缩放联动、>10 万点时序、多图层交互等自绘无法经济覆盖的需求；届时候选排序 = Visx（原语哲学一致）> ECharts 按需（性能强但治理代价高）。

### 2.2 symbols 大数据量渲染性能方案（分层闸门）

典型大型 ELF symbol 量级：5 万–50 万（个别 >100 万）。方案是三道闸门，顺序不可颠倒：

**闸门 1 — Core 侧聚合与裁剪（决定性，Rust 侧）**
- 可视化从不消费全量 symbols：Core 提供聚合查询端口——`section_summaries`、`top_symbols(section, n)`、`symbol_rollup(depth)` 等，聚合在 Rust 完成，**输出是快照的纯函数**，可 golden 测试、可进 CLI JSON。
- 这同时满足 IPC 红线（永不整体过通道）与确定性输出两条基线。Treemap 的每层 leaf ≤ 500 + `OTHERS (N more)` 聚合节点也在这一层裁决。

**闸门 2 — 分页与游标（IPC 层）**
- 明细表沿用 `query_symbols` 的 filter/sort/cursor/limit 契约（FS-TECH-015 §3 已定义），页大小上限进 config。排序稳定性规则：地址 + 符号名 tie-break，保证同快照同顺序。

**闸门 3 — 前端虚拟化（渲染层，仅兜底）**
- `@tanstack/react-virtual`（≈4KB，MIT）+ 36px 固定行高（与 DESIGN.md 行高裁决完全一致，虚拟化实现因此极简）。100k symbols 即使一页 200 行，DOM 节点 ≈2.4k，60fps 无压力；只有页大小被调大时虚拟化才真正介入。
- 该依赖满足准入清单：维护度（TanStack 活跃）、许可证 MIT、体积、无 native/WebView 影响。需记入依赖基线（后续随实现 ADR 一并申报）。
- **明确排除**：前端全量加载后自己聚合（违反红线）、Canvas 表格自绘（失去可访问性与文本选择）、Web Worker 渲染（复杂度不划算，因为数据已经小了）。

### 2.3 treemap 与 stacked bar 实现成本

| 形态 | 实现方式 | 工作量 | 说明 |
|---|---|---|---|
| ranked bars | HTML table 内嵌 div/SVG 比例条，宽度=百分比，颜色=token 变量 | **S** | FS-UI-02 视觉稿已是该形态；≈1 个组件 + 排序稳定性测试 |
| compact stacked bar | 单行 SVG rect 分段 + 图例，段色取状态/section token | **S–M** | ≈150 行组件；注意 added/removed 段用 diff 浅底 token，禁 0 冒充 |
| treemap | `d3-hierarchy`（squarify，ISC 许可）算布局 → 自绘 SVG rect → 点击下钻（每层重新向 Core 要聚合数据） | **M** | ≈300–400 行组件含 hover/下钻/OTHERS 节点；leaf 上限 500；无动画（红线），用 ≤180ms 面板过渡；PRD 已把 richer treemap 列 P1，与本文结论对齐 |
| 跨 build 趋势（多 build 历史，P1 能力） | P1 先做"表格 + sparkline"，重量级联动趋势图 Post-GA | P1 部分 S，完整 M–L | sparkline 必须带基线轴（DESIGN.md 图表红线） |

**视觉一致性要求（全部形态通用）：** 颜色一律读 tokens CSS 变量（禁止组件内写死色值，FS-ENG-009 已有 drift 校验）；无渐变、无阴影、无描边动画；数字 mono；状态 icon+label。

## 3. 议题② 文档导出

### 3.1 总架构：一个 IR、多 renderer、一个通道

```text
core 报告模型（Report IR：snapshot 摘要/sections/symbols/diff/gate/evidence 状态）
        │  ReportRenderer 端口（FS-TECH-002 / FS-ENG-009 既有）
        ▼
crates/firmwaresight-report
  ├── json.rs        versioned JSON        ← 基线承诺（Bundle: analysis.json / release-manifest.json）
  ├── html.rs        自包含 HTML（模板）    ← 基线承诺（Bundle: release-report.html）→ 复用为 P1 share report
  ├── md.rs          Markdown（模板）       ← P1 新增
  ├── csv.rs         分表 CSV              ← P1 新增
  ├── xlsx.rs        rust_xlsxwriter        ← P1/P2 新增
  └── docx.rs        docx-rs               ← P2 新增（可选）
        │
        ├─ 触发点 A：Release Bundle（工程 P4）——固定清单、面向审计/归档
        └─ 触发点 B：应用内交互导出（P1+）——用户选格式另存，同一 renderer
```

- **不加新数据契约**：所有 renderer 的输入都是 core 既有模型（NormalizedArtifact/BuildSnapshot/Diff/GateResult），renderer 只做投影。新增的只有 renderer 本身与触发它们的 use-case 命令（`export_report(format, selection, dest)`，use-case 型命令，符合 FS-TECH-015 §1）。
- **UI 不做格式转换**：前端只发命令、收结果路径/预览，不出现任何"前端拼 Excel"的逻辑（UI 不复刻核心逻辑红线）。
- **不新增 crate**：xlsx/docx 等以 feature/模块形式进 report crate，4 crate 上限不动；若 report crate 依赖总量超阈值（预计不会，见 3.2 体积列）再议 ADR。

### 3.2 逐格式评估

**① HTML（自包含单文件）— S → M｜P0 已有最小版（工程 P4 Bundle），P1 增强**
- 现状：Bundle 的 `release-report.html` 是基线承诺。技术路线 = `minijinja`（活跃，Apache-2.0，≈200KB 编译增量）模板 + **内联 CSS + 零 JS 或 <10KB JS**，单文件双击即读、离线可转发。
- P1 的 "HTML share report"（PRD 已列）= 同一模板管线加参数（含 sections/symbols 汇总 + 内联 SVG 图表：ranked bars/stacked bar 在 HTML 里就是静态 SVG，不引前端运行时）。
- 确定性：**完全可行**——无随机 ID、时间取快照、成员顺序固定，golden 逐字节校验（`crates/firmwaresight-report/tests/golden/` 已规划）。
- 陷阱：内嵌 SVG 图表必须在 renderer 侧从同一份 IR 生成（防 UI 与报告两套图表逻辑漂移）；文件名/标题含版本号时防路径注入。

**② Markdown — S｜P1**
- `minijinja` 输出 md，零二进制依赖。用途：贴 issue/PR/wiki/评审纪要。Bundle 的 `release-notes.md`（如有）已是 md 家族成员，模板化是自然延伸。
- 确定性：完全可行。陷阱：表格内竖线转义、长 symbol 名截断策略要进 golden。

**③ CSV — S｜P1**
- `csv` crate（BurntSushi，事实标准，MIT/Unlicense）。**按主题分文件**：`sections.csv`、`symbols.csv`、`diff.csv`、`gate_results.csv`——单文件混合多表是反模式。
- 确定性：完全可行。陷阱（必须在实现时裁决并写 golden）：
  - Excel 打开 UTF-8 乱码 → 默认写 UTF-8 BOM（并文档化该裁决）；
  - `added`/`removed` 行的 old/new 值：**空单元格表示"不存在"，严禁 0 冒充**（DESIGN.md diff 红线在数据层的直接映射）；
  - bytes 保持整数不千分位，delta 保留显式 +/- 号；
  - CRLF（RFC 4180 + Excel 友好）。
- 局限：CSV 不承载 Gate 结论排版与证据链，定位就是"给 Excel 的原始表"。

**④ XLSX — M｜P1 末–P2 初（取决于 P1 排期）**
- 选型 `rust_xlsxwriter`（jmcnamara，纯 Rust 无系统依赖，经外部检索确认活跃 v0.93+，MIT/Apache-2.0 双许可，支持格式化/冻结窗格/constant memory）。**排除**：C 绑定版 xlsxwriter（native 构建违背纯 Rust 分发）、umya-spreadsheet（读写双功能但更重，我们只写）。
- Sheet 结构建议：`Summary`（build identity + FLASH/RAM + Gate 五态统计）→ `Sections` → `Symbols`（top-N，非全量，注明总数与筛选条件）→ `Diff`（如有）→ `Gate`（rule/state/evidence/remediation 四列）。
- 确定性：**可行但需 spike 验证两点**——docProps 的 created/modified 时间戳（用 `set_properties` 固定为快照时间）、zip 成员顺序与 mtime。若库层不可控，外围 zip 重打包兜底（工作量 +0.5 人日）。
- 体积：纯 Rust 增量 ≈1–1.5MB 编译产物（zip/flate2 为主），可接受。
- 受众对应：Persona C（QA/合规"Excel 汇总"）与 Team 档（共享 policy/审计）的直接卖点，商业上值得排 P1。

**⑤ DOCX — M–L｜P2（可选）**
- 选型 `docx-rs`（bokuweb，纯 Rust，MIT；经检索 2025 年仍被主流项目采用）。docx 本质 zip+OOXML，技术可行。
- 成本真相：生成文件容易（S），**做出"仪器打印件"级别的排版体系才是成本**（M–L）——标题层级/表格样式/mono 字体映射/状态色打印适配/页眉页脚，都要从 IR 建一套 OOXML 映射并出 golden。
- 确定性：可行，内部 XML 成员顺序与时间戳需固定（同 XLSX spike）。
- 降级方案：**DOCX 的绝大多数受众需求已被"自包含 HTML + 打印为 PDF/Word 另存"覆盖**。建议 P2 仅在出现明确付费信号后再做，并先 spike docx-rs 表格样式能力（1 人日内可验证）。

**⑥ PDF — 原生排版：不做；HTML 打印视图：Post-GA 可选**
- 方案矩阵与陷阱：

| 方案 | 工作量 | 结论 |
|---|---|---|
| printpdf / pdf-writer 自建排版 | L–XL（文本换行/分页/表格全自研） | 排除 |
| typst 作为库嵌入 | M–L，但编译产物 +15–30MB，且字体子集化/CJK 体积问题；安装包从 ≈10MB 级膨胀到 40MB+，违背轻量分发（Windows NSIS 首要平台） | 排除（除非未来 Pro 档出现强需求且接受体积，须 ADR） |
| headless Chromium/wkhtmltopdf | +100MB 级外部二进制 | **绝对排除**（本地优先红线） |
| **HTML 打印视图**：report.html 加 `@media print` 分页样式，用户浏览器/系统 WebView Ctrl+P | S（在 P1 HTML 增强上 +0.5–1 人日） | **推荐**：零新增格式、单一真源；代价是打印输出非逐字节确定——对"人看的报告"可接受，对"归档"用自包含 HTML 替代 |

- 陷阱总结：PDF 的确定性承诺是最常见的自我埋雷——字体、分页点因环境漂移；FirmwareSight 的确定性基因要求我们对**格式承诺逐字节复现**，PDF 做不到，就明确不承诺，改由 HTML 承担归档职责。

**⑦ JSON（analysis.json / diff.json / release-manifest.json）**：非新增项，Bundle 已含、CLI 已有，renderer 复用。**⑧ CycloneDX SBOM**：PRD 已列 P1，serde 序列化，S，走同一 IR 通道。

### 3.3 确定性与离线：横向实现规则（全格式生效）

1. **内容 = 快照的纯函数**：一切时间字段取 BuildSnapshot 的可信时间，禁用导出时刻 `now()`。
2. **排序全显式**：符号/section/规则条目的输出顺序用「语义键 + 地址/ID tie-break」，杜绝 HashMap 迭代序泄漏（Rust 侧 known pitfall）。
3. **容器级确定性**：zip 成员排序 + 固定 mtime + 固定 doc properties（XLSX/DOCX spike 验证点）。
4. **golden 逐字节校验**：每格式 ≥2 套样张（最小 build / 含 diff+gate 的全量 build）进 `crates/firmwaresight-report/tests/golden/`；变更走人工评审（基线红线：严禁机械批量更新）。
5. **完全离线**：全部所选库无网络调用、无系统 Office 依赖；许可证全部 MIT/Apache-2.0/ISC，符合 07_COMPLIANCE 许可政策。
6. **Unknown 呈现一致性**：报告中 `Unknown` 用中性灰 + 空心标记（与 UI/设计稿同源），CSV/XLSX 中用显式 `unknown` 值 + 空单元格语义，永不冒充 Observed/0。

## 4. 与 report crate / Release Bundle 的关系

**裁决：复用现有通道，不另起炉灶。**

| 维度 | Release Bundle（现有通道） | 应用内交互导出（P1 新触发点） |
|---|---|---|
| 定位 | 发布证据链，面向"审计/归档/脱离 FS 可独立验证"（PRD 验收） | 用户便利，面向"拿走分析结论给别人看" |
| 内容 | **保持基线清单不变**（SHA256SUMS/manifest/release-report.html/release-notes.md/analysis.json/diff.json） | 用户按需选：HTML/MD/CSV/XLSX(/DOCX) |
| 确定性要求 | 逐字节（golden） | 逐字节（同 renderer 同规则） |
| 实现 | report crate 的 json.rs/html.rs | 同一批 renderer，仅多一个 `export_report` use-case 入口 |

- 两条通道**共用同一 IR 与 renderer**——差异只在触发点与文件集，杜绝"Bundle 报告"与"导出报告"两套逻辑漂移。
- **Bundle 清单不扩**：xlsx/docx 不进 Bundle（体积与受众都不合理；需要的人用交互导出）。未来若要扩 Bundle 清单，按基线纪律走 ADR（release-manifest schema 是 versioned public contract）。
- report crate 依赖增量预估（全部 renderer 落地后）：minijinja + csv + rust_xlsxwriter + docx-rs ≈ 3–5MB 编译产物、零系统依赖、零网络——对 Tauri 桌面包影响可忽略；`tauri-plugin-dialog`（基线已允许）承担"另存为"文件选择。
- Crate 纪律：不新增第 5 个库 crate；renderer 是 ReportRenderer 端口的多实现，与"Adapter-driven"完全同构。

## 5. 不值得做的格式（负面清单）

| 格式 | 不做的理由 |
|---|---|
| **原生排版 PDF**（printpdf/typst/Chromium 任一路线） | L–XL 投入换 HTML 打印 1 人日就能覆盖的需求；typst/Chromium 爆安装包体积；PDF 无法承诺逐字节确定性，与产品"可复现"基因冲突。Post-GA 仅存"HTML 打印视图"一条低成本口子 |
| **PPTX** | 目标用户（固件工程师/Lead）的证据链场景是报告+表格，不是 deck；Rust 侧无成熟维护库；要讲 PPT 的人会自己截图 |
| **RTF / ODF（.odt/.ods）** | docx/xlsx 已覆盖其受众；LibreOffice 环境在目标人群占比低；纯增维护面 |
| **带公式/透视表的"活" XLSX** | 静态数据导出即可；公式与透视是确定性陷阱 + 版本地狱，且违背"报告是证据不是分析器"的定位 |
| **图表 PNG 导出**（SVG 光栅化，如 resvg） | 自包含 HTML 已内嵌 SVG 矢量图；PNG 仅服务"贴 PPT"场景，用户截图成本为零；resvg 引入字体光栅化一堆复杂度 |
| **前端本地生成导出文件**（JS 侧拼 xlsx/docx） | 架构红线：UI 不复刻核心逻辑；导出必须走 Core 才有确定性与 golden。此项作为"反模式"写明，防止未来图省事在前端塞 SheetJS 类库 |
| **自研二进制报告格式** | versioned JSON 已是公共契约，自研格式是负资产 |

## 6. 前置验证（spike 清单，均为 1 人日内项）

1. **rust_xlsxwriter 确定性**：固定 properties + zip 成员序后，同输入两次导出逐字节比对；失败则评估 zip 重打包兜底。
2. **docx-rs 表格样式能力**：1 页样张验证表头样式/mono/行合并/列宽控制（P2 决策输入）。
3. **treemap 500-leaf 下钻**：真实 fixture（≥10 万 symbols）上 Core 聚合 + SVG 渲染帧率与 IPC 载荷实测。
4. **d3-hierarchy squarify 稳定性**：同输入布局逐像素一致（含 tie-break 排序）验证，进 golden。
5. **虚拟化行高锁定**：36px 行高下 `@tanstack/react-virtual` 与 sticky header/排序的兼容性。

## 7. 需要拍板的开放问题

1. **P1 排期权重**：可视化四件套（ranked bars/stacked bar/虚拟化/treemap 首版）与导出四件套（HTML/MD/CSV/XLSX）都在 P1，若需取舍，我的排序建议 = **虚拟化表格 + ranked bars → HTML 增强 → CSV/MD → treemap → stacked bar → XLSX**（先保判断力，再保可携带性）。
2. **Bundle 清单是否永久锁定**：本简报按"锁定、扩展走 ADR"评估，若产品侧希望 Bundle 直接携带 XLSX 汇总表，需提前在 ADR 中定 schema 版本策略。
3. **PDF 的产品口径**：是否接受"官方不支持 PDF 格式，提供 HTML 打印视图"的用户沟通口径（避免支持成本）。
