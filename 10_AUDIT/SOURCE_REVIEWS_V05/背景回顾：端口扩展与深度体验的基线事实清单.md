# 背景回顾：端口扩展与深度体验的基线事实清单

> **任务来源**：用户提出 Post-MVP 探索议题（不纳入 MVP）——①探索更多"端口"（产品的输入/输出/集成接口），让产品从单一分析工具长成嵌入式工作流枢纽，产生粘性；②人群窄，深耕现有四类 Persona 的使用体验。用户同时给出价值判据金句：**"通用的目的不是功能多，而是让用户走得慢；便捷的目的不是好用，而是让用户不想走。"**
>
> 本文从 v0.3.0 基线与群内已产出文件中提取与"端口/扩展点/粘性/深度体验"相关的**全部既有事实与约束**，供后续探索输出对齐，避免重复论证或踩线。
>
> **标注规则**：【硬约束】= 现有治理已锁死，任何新方案不得违背（违背必须走 ADR/用户裁决）；【可扩展空间】= 基线未锁死、留有演进余地，但推进须按既定流程（ADR / 阶段门 / 依赖纪律）。

## §1 议题原文与定位

| 议题 | 内容 | 与基线的直接对应物 |
|---|---|---|
| ① 端口扩展 | 更多输入/输出/集成接口，从单一分析工具长成"嵌入式工作流枢纽"，产生粘性 | 架构层：Ports & Adapters 四端口已就位且"future CI/headless 不需要重写"（FS-TECH-002）；产品层：CI integration / Team Policy / shared release evidence 均已锚在 Growth（FS-DEL-001）；watch、命令面板、协作面、通知等基线**零出现** |
| ② 深耕四类 Persona | 人群窄，深挖 Firmware Engineer / Lead / QA / Founder 的使用体验 | 四类 Persona 已定义（FS-PRD-003）；体验纪律已有完整基座：设计哲学五原则（FS-DESIGN-001）、voice 三原则（FS-BRAND-003）、G2 六项体验指标（FS-DEL-006）；History/onboarding 分别锚在 P1/P5 |

**三条定位性事实：**

1. **Post-MVP 定位本身是既有裁决**：当前 ACTIVE_TASK=NONE 阶段纪律、开发纪律三问（06_DELIVERY/05 §32）、Scope Creep 四问（FS-PRD-004）决定了两个议题现在只能"探索"，不能进实现。【硬约束】
2. **术语澄清（防混淆）**：议题①的"端口"指**产品对外的输入/输出/集成接口**；基线 "Ports & Adapters" 的"端口"指**架构内部抽象**。前者多数是空白或 Growth 排期，后者是已冻结事实。下文分别用"产品端口"与"架构端口"指代。【硬约束（口径）】
3. **金句与基线的同构性**：金句为用户 2026-09-27 新表述，基线无原文，但方向完全同构——"让用户走得慢"≈ Evidence is one click away / Numbers need context（FS-DESIGN-001 P1/P2）与"深度＞功能数量"（FS-DEL-002 §7"完整工作流，而不是功能数量"）；"让用户不想走"≈ 基线已有的回归类指标：MVP Return intent ≥5/8（FS-DEL-002 §4）、V1 验证 repeat usage（06_DELIVERY/05 §11）、B1 验证 real recurring use（FS-DEL-001 P B1）。金句可直接用作后续探索输出的**验收标准**。【可扩展空间】

## §2 架构既有端口与插槽（对应要求①）

### 2.1 端口总纲

- **ADR-0007 Core-first Adapter-driven**（Accepted）：围绕 headless Rust Core 形式化 Ports & Adapters 边界。五条规则：domain facts 只在 Core；外部技术以 adapter 实现；use-case 命令在 application 层；interface 层不持有业务真相；adapter 类型不得漏进 Core 公共契约。依赖方向不可逆（"implementation may simplify module names but not dependency direction"）。【硬约束】
- **FS-TECH-002（System Architecture v0.2）四个既有架构端口**：Artifact Adapter（object/gimli/MAP 解析器）、Storage Adapter（rusqlite/SQLite）、Provenance Adapter（git CLI）、Report Adapter（JSON/HTML）。Interface 层两个入口：React Desktop、fwsight CLI。禁依赖：Core→Tauri/SQLite/Tokio/WebView；Parser→UI；UI→SQLite/文件系统直读。【硬约束】
- **最重要的架构背书**：采用此风格的明文理由包括 **"future CI/headless 不需要重写"**（FS-TECH-002 §1）。即"工作流枢纽"所需的 headless 复用能力，是架构当初写下的预留意图，不是新决策。【可扩展空间】
- **代码区规划（FS-ENG-009，群内已产出，DRAFT）**：Phase 0 library crate ≤4 = `firmwaresight-{core, artifact, storage, report}` + `apps/cli` + `apps/desktop/src-tauri`；report = 唯一报告生产者，实现 core 的 **ReportRenderer 端口**（versioned JSON + 自包含 HTML）；"宁缺勿滥，不为未来预留空 crate"。【硬约束（≤4 红线）+ 可扩展空间（新格式挂 ReportRenderer）】

### 2.2 Artifact/Map 端口现状（新增 toolchain 的插槽）

- MapAdapter 接口已定义：`detect(text/header) -> confidence`；`parse(...) -> NormalizedMapEvidence`（FS-TECH-017 §6）。MVP 仅 GNU ld。**禁止**一个大正则"通吃所有 MAP"，必须按 toolchain 分离：`gnu_ld / armclang / iar / future adapters`（FS-TECH-004）。【硬约束】
- "future adapters" 是明文插槽：新工具链 = 新 adapter 实例 + fixture 门禁，不改架构。【可扩展空间】
- 归一化纪律：parser 特有事实必须先变成 stable core model 再持久化；UI 永不直接渲染 `object::Symbol` 或 parser 特有类型（FS-TECH-017 §8）。任何"端口"的输出想进 UI，必须走同一条归一化管道。【硬约束】

### 2.3 ReportRenderer 端口（新增输出格式的插槽）

- 报告只能由 report crate 生产（versioned JSON schema + 自包含 HTML，golden 机制锁版）；P0 骨架、P4 完整实现（FS-ENG-009；FS-TECH-013；ADR-0011）。desktop/ui 层自行渲染 = 违规。【硬约束】
- md/docx/xlsx/csv/pdf 等新输出格式 = ReportRenderer 端口的新实现，属既有插槽（群内可视化/导出探索已论证归 P1 及以后、新依赖须过 FS-ENG-006 七问）。【可扩展空间】
- Release Bundle 品质基准（独立可读 / manifest hash / preview / conflict-safe / progress / 失败不留假完整）是任何新导出物的事实天花板（FS-TECH-013；FS-PRD-002 P0-6）。【硬约束】

### 2.4 Provenance 端口

- v0.2 决策：用系统 `git` CLI 做**只读** provenance adapter（FS-TECH-023 / ADR-0017）；不引入 gix；换 gix 触发条件已写明（无系统 Git / 性能瓶颈 / 兼容负担），且必须 ADR。【硬约束】
- 降级语义：Git 不可用时分析照常、provenance=Unknown、Git 相关 Gate 规则转 Review/N/A。【硬约束】
- 这是产品目前**唯一**与外部系统对话的通道之一（另一个是文件系统输入）。【事实陈述】

### 2.5 Storage 端口

- SQLite（rusqlite bundled）= 本地结构化真相，为 build history / artifact 索引 / 100k+ symbols / evidence 关系 / gate history 而生（FS-TECH-016）；初始逻辑表已含 `gate_runs / gate_findings / release_records`——History 与审计的数据地基已预留。【硬约束（架构）+ 可扩展空间（History 类产品能力建在其上）】
- SQLite 文件是实现细节、**不是**交换格式；可移植输出只有三类：versioned JSON / HTML report / Release Bundle（FS-TECH-016 §9）。任何"数据出口端口"不得把 SQLite 直接当 API 暴露。【硬约束】
- workspace 布局已预留：`.firmwaresight/`（project.json / index.sqlite / snapshots/ / **reports/** / cache/ / logs/）；`firmwaresight.toml` 可入 Git（FS-TECH-005）。【硬约束】

### 2.6 IPC use-case 边界（新"产品端口"进 UI 的唯一通道）

- Tauri command 必须=用户 use case：好例子 `open_project / import_artifact / get_analysis_summary / query_symbols / compare_builds / run_release_gate / prepare_release_bundle`；坏例子 `read_file / execute_shell / run_sql / get_any_path`（FS-TECH-015）。【硬约束】
- DTO：Serde 可序列化、bounded、稳定 ID、永不暴露 rusqlite/Tauri 类型；大数据分页；错误 envelope（code/message/operation_id/details?/remediation?）。【硬约束】
- 版本口径：IPC 前后端同船发布，MVP 不做公共 API 语义版本；但 **release manifest 等 portable schema 是版本化公共契约**。【硬约束】
- 能力最小化：前端默认无通用 fs/shell 权限，dialog plugin 仅限显式文件选择，MVP 不启用 updater/network plugin（FS-TECH-011/014；基线 AGENTS.md）。【硬约束】
- 推论：watch、自动发现、通知等任何新"输入端口"进桌面端，都必须以新 use-case command 形式过此边界。【可扩展空间（形式）+ 硬约束（边界不可绕）】

### 2.7 CLI 归属口径

- CLI（`fwsight`）= 与 Desktop **平级的 Interface 层第二入口**（apps/cli），不是插件、不是 use-case 的重复实现，事实必须同源于 Core（FS-TECH-002；FS-ENG-009；FS-PRD-004 In Scope"CLI 与 Desktop 共用 Rust Core"）。MVP application 编排先放各 binary 内，desktop/CLI 出现明显重复后才抽 `firmwaresight-app` crate（FS-TECH-002 §5）。【硬约束】
- 6 命令面：`analyze / diff / gate / release prepare / project doctor`（FS-TECH-008）；默认 human-readable，`--json` 稳定 schema；stdout=结果、stderr=诊断；exit codes 0/2/3/4/5/6、10+ 保留；**CI 不允许通过解析自然语言判断结果**；`--json` 无 wall-clock 字段、路径 project-relative；不覆盖已有 bundle（需 `--force`）。【硬约束】
- **US-005 已按 CI 消费者设计**："作为 CI，我可以无 GUI 分析与 gate"（非交互/JSON/稳定 exit codes/不依赖桌面进程，FS-PRD-005）。即 CLI 是产品现成的、唯一"机器消费入口"。【硬约束（形状）+ 可扩展空间（CI 集成建在其上）】
- **口径警告**：FS-ENG-007《CI/CD Baseline》是 FirmwareSight **自身研发**的 CI（ci.yml/security.yml/release.yml），与"用户在其 CI 中使用 FirmwareSight"（产品 CI 集成）是两回事，探索时不得混引。【硬约束（口径）】

### 2.8 配置端口（已就位的"团队触点"）

- `firmwaresight.toml`：可入 Git、human-readable、team policy 可复现、不含 secrets、相对路径优先；unknown keys=warning（同 major schema 内）、invalid type/不支持的 schema_version=hard error、config 错误不允许被默认值悄悄覆盖（FS-TECH-009）。【硬约束】
- 建议"什么进 Git"：firmwaresight.toml + **team gate policy** + optional component declarations（FS-TECH-005）。这是产品当前唯一的团队协作原语（"配置即代码"）。【硬约束（事实）+ 可扩展空间（Team Policy 的地基）】

### 2.9 工具链支持矩阵现状与 R2

- MVP 支持矩阵（FS-TECH-004）：ELF 32/64 = Yes（sections/symbols/基础 metadata）；GNU ld `.map` = Yes；`.bin`/Intel HEX = Basic（hash/size/package only）；Git repo = Yes（commit/tag/dirty/provenance）；**Keil `.axf` = Experimental until fixtures**（"often ELF, but do not blanket promise"）；**ArmClang map = P1（adapter）**；**IAR `.out/.map` = P1/P2（adapter）**；COFF/PE = No MVP promise（future）；SREC = P1（basic metadata）。【硬约束（现状）】
- "能打开"≠"支持"：Supported 四门槛 = fixture + parser tests + known limitations + UI capability reporting（FS-TECH-004；FS-DEL-002 §5 未达门槛只能标 Experimental/Partial/Unsupported）。【硬约束】
- ADR-0006：MVP 正式支持 ELF 32/64 + GNU ld MAP + BIN/HEX 基础 + Git provenance；**Keil/ArmClang/IAR 只有在 fixture + adapter tests 完成后才升级 Supported**；"范围小，但可信"。【硬约束】
- R2（Toolchain fragmentation）：缓解 = support matrix + adapters + no universal parser claim + **fixture-driven expansion**（FS-RSCH-004）。工具链扩张的节奏被 fixture 门禁锁死——扩张方向开放、扩张速度不自由。【硬约束（节奏）+ 可扩展空间（方向）】
- P5 Productization 才建完整 Toolchain Compatibility Matrix：GNU Arm Embedded / Zephyr GCC / ESP-IDF = Supported，ArmClang / Keil AXF = Beta，IAR = Experimental（06_DELIVERY/05 §15）；v1.0 兼容性底线 = "GCC + 一个重要商业 Toolchain"（06_DELIVERY/05 §25）。【硬约束】
- 能力报告是每次 import 的义务：逐源展示 Supported/Available/Missing/Not provided，不因缺某一来源让整个 build 失败（FS-TECH-004）。【硬约束】

### 2.10 两条与"端口/集成"直接相关的硬边界

- **ADR-0004 Local-first**：MVP local-first/offline-first，核心能力不依赖登录或服务器；后果明写"云协作延后"。【硬约束】
- **ADR-0013 Network Client Deferred**：MVP bootstrap 不含 HTTP client/TLS 依赖（Reqwest+Rustls 是唯一被批准的未来路线，触发条件=签名更新/CVE feed/licensing/optional cloud 需要时）。任何联网型"端口"（云同步、在线 feed、遥测）都被此 ADR 挡在 MVP 外。【硬约束】
- **ADR-0005 No AI in Trusted Core**：生成式 AI 不参与 parsing/diff/gate/hash/SBOM 事实生成/release decision；未来 AI 只能解释/搜索/总结且必须标 advisory。"智能枢纽"若涉 AI 判断，此红线先于一切。【硬约束】

## §4 产品纪律（对应要求③）

### 4.1 Non-goals

- Explicitly Out of Scope 八项（FS-PRD-004）：不做 IDE（不编辑 C/C++ 源码/不做 LSP/不做编译器前端）；不做 Debugger（JTAG/SWD/GDB server）；不做 Flasher；不做 HIL；不做 Firmware Reverse Engineering Suite（不做 binwalk 替代/漏洞利用分析）；不做 Cloud SBOM Platform（MVP 不要求账号/云端）；**不做"AI 判断能否发布"**（Gate 必须 deterministic policy）；不承诺所有 ELF 等价（必须显示 evidence availability）。【硬约束】
- 章程非目标（FS-GOV-002 §6）：当前阶段不追求替代 Keil/IAR/VS Code；烧录、调试、示波器、HIL；自动生成固件；自动漏洞利用分析；云端设备管理；法律合规认证；**万能支持所有 toolchain**。【硬约束】
- 对议题①的含义："嵌入式工作流枢纽"的枢纽边界 = 构建产物 → 证据 → 交付，**不向编码侧（IDE）和执行侧（烧录/调试）延伸**。【硬约束】

### 4.2 三张"推迟/禁止"清单的差异化语义（易错点）

| 清单 | 出处 | 语义 |
|---|---|---|
| MVP 不应该做什么 | 06_DELIVERY/05 §8 | Cloud/Account/Team workspace/License system/**Plugin marketplace**/AI assistant/CVE cloud service/Auto update/Dark theme/Custom dashboard builder/Complex graphs/Remote artifact repository/Firmware flashing/HIL/JTAG-SWD/OTA——"以下全部推迟"【硬约束（对 MVP）】 |
| Deferred by design | FS-DEL-002 §7 | account/cloud/team/AI/SBOM/CVE/updater/dark mode/**plugin**/HIL/flashing/OTA——"以下缺失不会阻止 MVP"；MVP 完整性=**完整工作流，而不是功能数量**【硬约束（对 MVP）】 |
| 产品不要直接跳到 | 06_DELIVERY/05 §27 | AI Chat/Cloud Dashboard/**Plugin System**/Firmware Flashing/Device Management/OTA/Full Vulnerability Scanner/HIL/Source Code IDE/**Build System**——"听起来像完整产品，但很容易让项目失控"，不是 v1.0 完整性要求【硬约束（对 v1.0）】 |

- 关键读法：**plugin 被"推迟/不跳"，但从未被宣布永久禁止**；同时 plugin marketplace 被 FS-DEL-006 点名进"不自动扩展"清单。产品端口探索若演化为插件机制，必须 ADR + 用户裁决，且时机只能在 Growth 之后。【硬约束（时机与流程）+ 可扩展空间（是否与如何）】

### 4.3 四动词纪律

- 产品心智模型 = 四段式工作台：**Analyze 看清 build / Compare 看清变化 / Gate 看清风险 / Release 固化证据**（FS-PRD-001）。【硬约束】
- R6（Product becomes "feature pile"）头号缓解 = four verbs + roadmap gates + **ADR for scope expansion**（FS-RSCH-004）。【硬约束】
- v1.0 成熟范围 = 四动词 + History 全部成熟（06_DELIVERY/05 §25）；G6 完整性清单 = Analyze/Compare/Release Gate/Release Bundle/History/CLI/Installer/Signing/Update/Documentation/Commercial Distribution，并明言"完整产品≠功能最多"（FS-DEL-006）。【硬约束】
- 章程价值链表述：Understand → Compare → Verify → Package，**不是** Upload → AI → Magic answer（FS-GOV-002 §5）。【硬约束】
- 对议题①的含义：任何新端口都必须是四动词的**输入端/输出端/自动化通道**，不能成为第五动词。"枢纽"叙事必须长在四动词上（专业写手在可视化/导出探索中已确立同样的挂靠原则，可复用其论证）。【硬约束】

### 4.4 Scope Creep 四问与开发纪律三问

- 四问（FS-PRD-004）：①是否直接提升 Analyze/Compare/Gate/Release？②是否需要新增协议/硬件/运行时？③是否可在现有 fixture 中验证？④是否延迟 MVP？——**若 1=否 或 4=是，默认推迟**。注意第②问对"端口"议题杀伤力最大：多数集成接口天然"需要新增协议/运行时"。【硬约束】
- 三问（06_DELIVERY/05 §32）："我们顺便把 XXX 做了吧"→ 它属于哪个阶段？/ 当前阶段是否需要它？/ 没有它是否无法验证本阶段假设？→ 不影响当前阶段验证 = **默认不做**。【硬约束】
- 新功能过三问的等价纪律已写入基线 AGENTS.md 与本人治理摘要。【硬约束】

### 4.5 与两议题同构的既有原则（FS-GOV-002 §7）

1. Evidence before verdict；2. Deterministic before intelligent；3. **Local before cloud**；4. **Existing workflow before migration**；5. **Narrow compatibility before false compatibility**；6. **Fast time-to-value before platform ambition**；7.（证据可追溯贯穿）。——其中 3/4/5/6 正是"端口"议题的四条先天判据：端口应该是**嵌入既有工作流**（而非要用户迁移）、**窄而可信**（而非万能）、**本地优先**（而非云中心）、**不抬高 time-to-value**。【硬约束】

## §5 商业分层中与集成/粘性相关的表述（对应要求④）

### 5.1 三层结构（FS-PRD-006，"验证假设，不是最终定价"）

| 层 | 建议包含 | 与端口/粘性的关系 |
|---|---|---|
| Free | 单 build ELF/MAP Analyzer、基础 memory、symbol explorer、**单次 build diff**、本地使用 | 让工程师主动安装；"单次 diff"意味着 **Free 层无 History 粘性**【硬约束（假设存在）】 |

### 5.2 可收费价值判断（与"粘性"直接同构）

- "真正可收费的不是 treemap，而是：release risk reduction、**repeatability**、evidence package、**team policy、CI integration**、compliance preparation"（FS-PRD-006 §4）。——粘性被明文押在" repeatability + 团队/CI 集成"上，而非可视化炫技。【硬约束（商业判断）】
- 不采用的收费逻辑：不按文件大小/单次扫描/symbol 数量/每个 MCU 型号收费——"这些会惩罚正常使用"（FS-PRD-006 §2）。任何端口计费设计不得引入使用惩罚。【硬约束】
- 付费验证门槛（写 Team 能力前）：20 个目标用户访谈 + 8 个实际 artifact 试用 + 3 个明确付费意愿 + 1 个真实团队以自己的 release 流程试点（FS-PRD-006 §3；R1 未验证状态）。定价不冻结。【硬约束（流程门槛）】
- B1 阶段任务明列：pricing experiment、**Free/Pro boundary** 实验（FS-DEL-001）——分层边界本身是待验证变量。【可扩展空间】

### 6.2 Persona 逐个覆盖度要点

- **Persona A — Firmware Engineer**（STM32/ESP32/Nordic/NXP/Renesas；GCC/Clang/Keil/IAR；"build + copy files + tag"发布习惯；JTBD=交付 build 时快速确认内存/版本/二进制/Git 一致）：现有触点=Analyze/Compare/Bundle 全流程，但**每个触点都以"他记得打开 FirmwareSight 并主动拖文件"为前提**。产品在他的日常流（IDE→编译→烧录→测试）中零存在感；习惯回路类能力（watch/自动发现）完全空白。Keil/IAR 用户在其 MVP 窗口内只会得到 Experimental/P1 承诺。【推导盘点】
- **Persona B — Firmware Lead**（JTBD=要一份可复核的差异与证据，而不是开发者口头"应该没问题"；关注 regression/provenance/repeatability/team process）：Diff/Gate/Bundle 已直接命中 JTBD；但"复核"动作本身发生在聊天工具/邮件/会议里，产品无协作面（collaboration 仅在 Post-GA 清单出现一次）；regression 长期趋势依赖 History（P1）。【推导盘点】
- **Persona C — QA / Quality / Compliance**（JTBD=拿结构化证据，而不是临时向研发收集截图和 Excel）：Bundle（US-004）+ release-report.html 已覆盖"给证据"；取数导出（CSV/XLSX）已由群内写手件论证归 P1（Persona C 取数/Team 审计场景）；audit history 在 Team 层、SBOM 在 P1/P2。【推导盘点】
- **Persona D — Small Hardware Founder / CTO**（JTBD=没有专职 DevOps/安全工程师时，低成本把 release 做专业，不买重型企业平台）：四动词闭环+CLI 已给"专业感"；但**他最痛的恰是 CI 集成空缺**（没有 DevOps 意味着更依赖自动化），而 CI Integration 锚在 v1.0 后 §26——时机错配是本议题值得记录的事实。【推导盘点】

### 6.3 四类 Persona 共同的"未触达"汇总（探索弹药库）

1. **构建侧**：watch/目录监视/自动发现/构建 hook——零出现、零禁令，是最大纯空白（须过 IPC use-case command 边界 + 不做 IDE 红线内）。
2. **流水线侧**：CI 集成/门禁自动化/PR 回写——CLI 原语已就绪，集成锚在 v1.0 后；Team 层商业假设已押注。
3. **协作侧**：shared policy 深化/审计/协作流转/通知——Growth 排期与 Team 层假设已有，MVP 期只有"配置即代码"。
4. **记忆侧**：History MVP 缺位（P1 补上）——"单次 diff"的 Free 层无回访钩子；memory trends/release history 是"不想走"的现成载体。
5. **外部世界侧**：除只读 Git CLI 与文件系统外，产品不与任何外部系统对话——这是 local-first 的**设计代价**，也是"端口"议题的起点事实（联网类端口先撞 ADR-0013/0004）。

### 6.4 与"粘性"相关的既有度量锚点（深挖体验的现成验收口径）

- MVP：Return intent ≥5/8"下一次 release 愿意再次使用"、Discovery ≥30% 发现真实新信息、Analyze→Compare 完成 ≥60%（FS-DEL-002 §4；FS-DEL-006 G2）。【硬约束（指标存在）】
- V1：repeat usage 验证；B1：real recurring use、support cost；Growth：按真实付费需求逐步增加（FS-DEL-001）。【可扩展空间】
- 深度体验的既有纪律底座：设计哲学五原则（Evidence one click away / Numbers need context / Unknown first-class / One primary focus / Dense not crowded）；voice 三原则（说事实不做判决/说未知不填空/**给下一步**——"给下一步"本身就是留客机制的最小形态，Flow A 的 suggested next action 已在执行）；性能预算（First useful analysis<60s、500MB 不卡 UI）。【硬约束】

## §8 对接小结

### 议题① 端口扩展（从分析工具到工作流枢纽）

- **已就位**：四个架构端口+插槽语义（MapAdapter/future adapters/ReportRenderer）；IPC use-case 边界与 CLI 双入口；"future CI/headless 不需要重写"的架构背书；firmwaresight.toml+team policy 入 Git 的团队原语；DB 层 History/审计地基；CI/SBOM/Team Policy/shared release evidence 的 Growth 排期锚点；CLI 已按 CI 消费者设计。
- **空白（探索空间）**：watch/目录监视/自动发现（零出现零禁令）；命令面板（零出现零禁令）；决策协作面与通知；PR/工单回写；导出格式扩展（挂 ReportRenderer）；工具链 adapter 扩张（ArmClang P1/IAR P1/P2 的落地路径）。
- **红线（不可触碰）**：不做 IDE/不替代 Keil-IAR-VS Code；AI 不进可信核心；MVP 不联网（ADR-0013/0004）；Growth 四不破坏；plugin marketplace 在"不自动扩展"名单；新端口必须以 use-case command 过 IPC、新依赖过 FS-ENG-006 七问、范围扩张走 ADR+Scope Creep 四问；端口必须挂靠四动词。

### 议题② 深耕四类 Persona（让用户走得慢、不想走）

- **已就位**：四 Persona+JTBD 定义；设计哲学五原则与反模式；voice"给下一步"；Flow A-E 全链路（含 parse failure 的"不许只显示 Import failed"）；性能预算；History P1 排期；P5 onboarding/sample project/settings/a11y；G2 六项体验指标与 Return intent 口径。
- **空白（探索空间）**：MVP 无 History（记忆侧断档）；Free 层无回访钩子；习惯回路空白（见议题①构建侧）；Persona D 最痛的 CI 集成排期错配；Persona B 的复核协作面空白；Persona C 的取数导出待 P1。
- **红线（不可触碰）**：深挖体验≠加功能（R6+三问四问全适用）；"让用户走得慢"不得做成 dashboard 化/营销化（设计反模式禁入）；不显示空壳导航（History 未实现不得上导航）；体验改动不得让 UI 复算 core 事实。

### 共同提醒

两个议题的合法推进路径只有一条：**探索与提案先行，实现让位于阶段门**——现处 ACTIVE_TASK=NONE，任何具体化都必须先过"属于哪个阶段/当前阶段是否必须/没有它是否无法验证假设"，再按 ADR（技术基线变更）与 Scope Creep 四问（范围扩张）走流程；用户金句（走得慢/不想走）可作为提案的**价值判据**，但不能替代上述门禁。
