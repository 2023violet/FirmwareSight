@群管理员 README + 01_PRODUCT 全部 7 份文档已精读，结构化理解摘要如下：

【1. 核心问题】小型嵌入式团队发固件时靠手工拼接 Git 状态、ELF/MAP、hash、版本号、memory 报告与三方组件清单——易遗漏、不可复核、难交接。FirmwareSight 定位"本地优先的固件发布工作台"，四段心智模型：Analyze 看清 build → Compare 看清变化 → Gate 看清风险 → Release 固化证据。主张 Know exactly what ships，不改造构建系统、不上云、不做"理解一切"。

【2. 目标用户与场景】四类 Persona：A 固件工程师（交付前确认内存/版本/二进制/Git 一致，防发错版本）；B 固件 Lead（要可复核的 diff 与证据，而非口头"应该没问题"）；C QA/合规（拿结构化证据包替代截图+Excel）；D 小硬件创始人（无专职 DevOps 也要专业发布）。明确不优先：大型 HIL 汽车团队、纯 Linux/容器供应链团队、逆向安全实验室、OTA fleet 平台。

【3. MVP 范围与 Non-goals】P0 六能力：① Artifact Import（ELF/GNU ld MAP/BIN·HEX 基础信息+可选 Git，原文件只读、记 SHA-256、fail closed）；② Build Analysis（arch/endian/entry/sections/FLASH·RAM 占用/symbols/top contributors/build-id）；③ Build Diff（FLASH/RAM/section/symbol 级 delta，可 drill down，禁止只给"+8KB"）；④ Build Identity（hash/commit/tag/dirty/toolchain/version/timestamp 可信类型）；⑤ Release Gate（10 条 deterministic 规则，结果仅 PASS/REVIEW/BLOCK/NOT_APPLICABLE）；⑥ Release Bundle（SHA256SUMS/manifest.json/report.html 等，不签名不上传）。
Non-goals（写死）：不做 IDE、不做 Debugger/JTAG、不做 Flasher、不做 HIL、不做逆向套件、不做云 SBOM、不用 AI 判断能否发布；不承诺所有 ELF 等价（必须展示 evidence availability）；Scope Creep 四问判定，命中即默认推迟。

【4. 验收标准要点】首次有效分析 <60s；≤500MB 工作集 UI 不卡死；fixture 解析成功率 100%、受支持格式不允许 crash；不支持文件明确报错原因；缺 debug info 不崩；结果必含 artifact hash；Diff 明确 old/new、正负号、added/removed/changed 分列、可导出 JSON/HTML；Gate 每项含 rule/state/evidence/remediation，Review 与 Block 视觉区分，Unknown 不得自动 Pass，policy 可存 project config；Bundle 脱离 FirmwareSight 可独立阅读、含全量 hash、不覆盖已有目录除非用户确认；CLI 非交互、JSON 输出、稳定 exit codes。NFR：离线可用、输出可复现、Windows 首要平台。

【5. 商业模式假设】PLG 三层：Free（单 build 分析/基础 memory/单次 diff，目标工程师主动安装）→ Pro 个人（无限历史/Gate/Bundle/CLI/policy/组件证据/SBOM）→ Team（共享 policy/CI/审计/企业打包）。明确不按文件大小/扫描次数/symbol 数/MCU 型号计费。真正可收费的是 release risk reduction、repeatability、evidence、team policy、CI、合规准备，而非 treemap。付费验证门槛：≥20 用户访谈、≥8 真实 artifact 试用、≥3 明确付费意愿、≥1 团队试点；MVP 前不冻结价格。

【6. 发现的疑点/风险】
① CLI 归属口径不一：PRD 把"CI/headless CLI"列 P1，Scope 的 In-Scope MVP 又写"CLI 与 Desktop 共用 Rust Core"，US-005（CI 用 CLI）也未标阶段——MVP 是否含 CLI 建议冻结口径；
② Persona A 覆盖 Keil/IAR 用户，但 Keil/ArmClang MAP adapter 是 P1，MVP 实际主打 GCC/Clang，早期可服务人群窄于 persona 描述；
③ FLASH/RAM 分类规则未在产品文档定义（如 .data 同时占 RAM 与 FLASH load image，跨工具链归属是解析高风险点）；
④ "project version（声明或解析）"与"timestamp 来源/可信类型"在 P0 层面仍含糊，需指定解析来源与降级行为；
⑤ 无 Git 仓库时 Gate 前 3 条规则的行为未见明文（推测 NOT_APPLICABLE，需确认）；
⑥ 商业张力：Free 档只覆盖 Analyze/单次 diff，差异化最强的 Gate/Bundle 全在付费层——免费漏斗验证不到核心价值，且"单次 diff vs richer diff"的边界偏模糊。

【FirmwareSight 品牌与设计基线 · 结构化理解摘要】
范围：README + 02_BRAND 全部 3 篇 + 03_DESIGN 全部 6 篇 + assets/design-tokens.json

■ 1. 品牌定位与语调
· FirmwareSight = “Embedded Firmware Release Workbench”，tagline “Know exactly what ships.”（中文主张：每一次固件发布，都知道自己到底发布了什么）。衍生规范：CLI fwsight、firmwaresight.toml、.firmwaresight/；书写禁用 “Firmware Sight” / “Firmware-Sight”，FWSight 仅限 CLI/内部缩写。
· 品牌内核 “Clarity before release”：像一台可靠的工程仪器（precise / calm / inspectable / technical / restrained / trustworthy），明确拒绝赛博朋克、霓虹、“AI 魔法”、“one click compliance” 人设。
· 四大信息支柱：See the build / See the change / Verify the release / Keep the evidence。隐喻 = inspection bench / 光学仪器（工程放大镜），不是"扫描雷达"。
· 语调三律：说事实不做判决（“Git tree has 2 modified files” 而非 “Your release is unsafe”）；说未知不填空（unknown 版本不得编造）；给下一步。禁用词：guaranteed / fully compliant / zero risk / intelligent detection（若实为规则）等。

■ 2. 设计哲学核心主张
· 总纲 “Instrument-grade clarity”：UI 是仪器不是营销 Dashboard——帮用户判断，不替用户判断。
· 五原则：P1 Evidence 一键可达；P2 数字必须带上下文（相对谁/占比/最大贡献者/是否超预算）；P3 Unknown 是一等状态，不得藏成灰色空白；P4 一屏一个主焦点；P5 Dense not crowded（靠分组/对齐/排版，不靠卡片+阴影+颜色堆砌）。
· 反模式黑名单：玻璃拟态、紫蓝渐变科技感、一数据一卡、胶囊滥用、装饰动画、纯颜色编码状态、KPI 塞满首屏。主题策略：MVP 仅 Light（可读性/可打印/省双主题 QA），Dark 进 P1。

■ 3. 信息架构与关键 UX 流程
· 一级导航 6 项：Overview / Analyze / Compare / Release / History(P1) / Project Settings；未实现的功能不显示空壳导航。Overview 回答"这个项目现在能发吗"；Settings 只放项目级 policy，不与 app 级偏好混放。
· 五条关键流：A 首次分析（不设账号/配置墙，用能力 banner “ELF ✓ · MAP 未提供 · Git 未链接” + 推荐下一步）；B Compare（A/B 选择 → diff 摘要 → 点击最大增长贡献者 → 下钻 symbol → Evidence）；C Release Gate（Block/Review/Pass 分组 → 用户显式接受 Review → Bundle 预览 → 导出）；D 未知依赖（状态 “Detected / version unknown”，用户 Declare 后标 Declared，永不冒充 Observed）；E 解析失败（必须展示 magic bytes / 尝试的 adapter / 原因 / 支持格式 / Copy diagnostics，禁止只报 “Import failed”）。

■ 4. 视觉系统与组件规则要点
· 4px 网格八档间距（4–64）；圆角 6/8/10（pill 仅限紧凑状态标签）；1px 边框为主，阴影只给浮层（菜单/对话框/拖拽层）。
· 字体：系统 UI 栈 + mono 栈；层级 Page 20/28 · Section 15/22 · Body 13/20 · 表格 12–13/18 · 元数据 12/18，数字一律 mono。
· 颜色 = 14 个语义角色（bg×3 / text×2 / border / accent / status×4 / diff×3），色值以 design-tokens.json 为权威草案；状态必须 icon+text，不许只靠颜色。
· 布局：最低 1024×720，主设计 1280×800 / 1440×900；nav rail 220–240px；Evidence inspector 320–380px；表格优先用满宽度。
· 图表优先级：table > ranked bars > compact stacked bar > treemap（仅 size 构成）；禁 3D、滥用 donut、无基线 sparkline。动效 120–180ms，仅限面板开合/行展开/状态迁移/拖放反馈。
· 组件铁律：按钮仅 3 级（Primary/Secondary/Ghost，Destructive 是语义修饰非第四体系），一区最多一个 Primary；状态 5 态 PASS/REVIEW/BLOCK/UNKNOWN/N/A = icon+label+count；表格必须可聚焦/排序/mono 数字/空态/长路径截断+copy；Diff Row 必须同时给 old/new/delta，added/removed 禁用 0 冒充；Dialog 仅用于真正中断，Toast 只做瞬时确认，错误必须保留在可恢复位置。

■ 5. 可访问性要求
· 以 WCAG 2.2 AA 可操作原则为设计参考（桌面应用同样适用）：键盘可达、可见焦点、对比充足、不只靠颜色、语义化表头、icon button 有 accessible name、dialog focus trap、主要状态对读屏可理解。
· 快捷键：Ctrl/Cmd+O 打开、Ctrl/Cmd+K 命令面板(P1)、/ 过滤、Esc 关浮层；Tab 顺序=视觉顺序；尊重 prefers-reduced-motion；主工作信息字号 ≥12px（禁 11px 以下）。

■ 6. 疑点/风险（我的发现）
① tokens 版本错位：design-tokens.json 自标 v0.1.0 “draft”，却被 v0.3.0 基线指定为"权威"——建议升版或在 BASELINE 注记豁免。
② tokens 覆盖缺口：14 个角色只有单色值，缺 hover/pressed/disabled/focus ring、diff 浅底色、状态反白文字色；Visual System 提到的 shadow 与 pill 半径均未 token 化——组件库落地前必须补齐，否则必然出现私自造色。
③ 文档微冲突：Voice 定义 4 个状态，Component Rules 定义 5 个（多 N/A），N/A 的视觉/语义需补一页说明。
④ 对比度初算：浅色 14 色对白/浅底作正文均 ≥4.5:1（最紧的是 review 琥珀 #9A6700 ≈4.9:1，偏紧）；Dark 主题落地时需全量重验；diff 三色若未来兼作填充底色，需另备浅底变体。
⑤ Evidence Inspector 320px 要容纳 8 类字段（含 raw value/hash），实操偏挤，建议 P0 用真实数据验证后再定宽度。
⑥ 命名仅做过公开网络级初筛，商标/域名/商店上架前必须专业复检（文档已自我声明，属已知项）。
